# Security design: Cipherleaf

This record states what Cipherleaf protects, where its trust boundaries are, what it promises, and its known limitations. It describes the code as of amendments A9 to A22 (A22, from 2026-10-23, removed the suggested passphrase, its Copy button and the `eff-wordlist` crate, so that clipboard limit no longer applies; the credits work of the same day added `THIRD-PARTY-NOTICES.md` and no new promise; A20, Start over, merged into `main` on 2026-10-23 and not yet in a portable build; A21, the latest before A22, is from 2026-10-23: Cipherleaf is a notes app first, security (master password, auto-lock, screenshot protection) and Passwords (KeePassXC) are optional switches, commits `84b281d` and `0929ae5`, then the review fixes in `f9d2676`, which added promises P20 and P21, changed P7, P8, P11 and P18, and added the A21 limits below; A21 is built and tested on the owner's PC on throwaway data (draft [PR #3](https://github.com/AbyssWatcher2/CipherLeaf/pull/3), tested at head `5ef5b07`), not yet accepted; A19, commit `442036e`, added copies and a restore of the encrypted KeePassXC passwords file and a Quit that never force-ends KeePassXC, promise P18, and changed P11 and threat 6; A18, commit `1273093`, added the readable first-run passphrase and restore from backup, promise P17 and a clipboard copy of the suggested passphrase (removed again in A22); A17, commit `dc95fd3`, changed the lock sequence and added promise P16): passwords are kept in the bundled KeePassXC 2.8.0 (only while the Passwords switch is on), shown inside the Cipherleaf window, and Cipherleaf's own vault holds notes, sticky notes and settings. **Since A21 the master password is optional.** A vault can be open (no password, not confidential) or protected (master password); the person can switch between them at any time. Each promise is a claim to verify, not a guarantee. Update this file when a promise, boundary or limitation changes.

A dependency scan, a plaintext search or a passing test can support one specific claim. None of them shows on its own that the app is secure.

## What it protects

- **Cipherleaf vault contents:** notes and pages, sticky notes, pasted images and settings. **Since A21 this protection is confidentiality only while security is on.** With security off the contents are still in the encrypted, tamper-checked format, but the key is public, so they are not private (see the A21 limits below). Since A23 the screens do not call the notes "encrypted" while security is off.
- **Cipherleaf keys and credentials:** the master password, the optional keyfile, and the 256-bit data key that encrypts everything.
- **Passwords (A9):** usernames, passwords, TOTP secrets and attachments live in `data/passwords.kdbx`, protected by KeePassXC's own master password (and optional keyfile). Cipherleaf never decrypts, opens or interprets them. **Since A19 it does copy the encrypted file bytes** (on each lock, into `data/backups/`) and can replace the file from such a copy; it only checks the KeePass file signature (8 bytes) and the size.

## Trust boundaries

| Zone | Trust | What crosses the boundary |
|---|---|---|
| Disk / USB stick (`data/vault.clf`, `data/backups/`, `data/passwords.kdbx`) | **Untrusted.** Anyone may copy or modify these files. | Only ciphertext (an authenticated header and records for Cipherleaf's vault; KeePassXC's own encrypted format for passwords, including the copies `passwords-*.kdbx` in `data/backups/` and the `passwords-undo-*.kdbx` files from a restore) |
| Rust core (in-process) | Trusted. The only holder of Cipherleaf's keys. | — |
| UI (WebView2, same process) | Trusted to display data; never receives keys. | Decrypted note and sticky-note content it shows; the Cipherleaf master password while typing it |
| **Bundled KeePassXC (separate process, A9)** | **Trusted** as a mature, separately maintained program. Cipherleaf starts it only if its executable matches the verified 2.8.0 hash. | Cipherleaf passes only file paths and the options `--config`, `--localconfig` and `--lock`. For the in-window display (A10) it also changes KeePassXC's window style, owner and position (window handles and rectangles only). Since A19 it also asks KeePassXC to close like its close button does (on Quit and before a passwords restore) and never force-ends it. It never sees KeePassXC's master password or entries. |
| Windows (clipboard, screen capture, other processes) | Partly trusted | Window pixels of Cipherleaf (capture-protected). Passwords copied from KeePassXC are handled by KeePassXC. |
| Network | Untrusted; **unused by Cipherleaf's own code** | Cipherleaf's code has no network code. The Microsoft WebView2 component that draws the window was seen making outbound HTTPS connections at startup (live check 2026-10-23; contents not captured, address owner inferred). KeePassXC is preset to make no connections; the owner can turn features on in KeePassXC. |

Every app command is callable by any Cipherleaf window. So a script injected into the UI could read the vault while it's unlocked. Since A18 this includes `restore_vault`, which replaces the vault file and needs no re-authentication of the current vault (it needs the password of the backup being restored). The picked-path rule (see P17) limits what such a script could point it at. **Since A19 this also includes `restore_passwords`,** which replaces the KeePassXC passwords file. It is gated only by the unlocked state and the bare-name / picked-path rules (see P18); it asks for no password and the file is checked only for its signature and size. **Since A21 this also includes `enable_security`, `disable_security`, `set_passwords_enabled` and `start_notes`.** `disable_security` needs the current password (and keyfile) and is rate-limited like unlock. It is not the only way to lower security. `restore_vault` can turn security off for a vault that has a master password, when it is given a backup that was made with security off and `allowSecurityOff` is true. The checkbox in the restore dialog is only a UI gate, so a script injected into the UI could pass that value. `enable_security` needs no extra confirmation beyond the dialog in the UI and can delete earlier automatic backups that were made with security off (`remove_unprotected_copies`). A script injected into the UI could call it while the vault is open, and it would set a password the owner does not know. Both are callable by any window and are recorded as limits. `start_notes` creates a new open vault only when none exists. The mitigations are a strict Content Security Policy (no remote scripts, styles, images or connections), no remote content, image sniffing, and rejecting SVG.

## Threats it's designed to resist

1. **Stolen or copied vault or backup (offline guessing):** Argon2id with high memory cost, an optional keyfile, and a master-password rule (at least 10 characters and a zxcvbn score of 3 or more).
2. **Tampering with the vault file:** every record and the header are authenticated. Changed bytes, swapped records, records moved between tables or vaults, and edited key-derivation settings are all detected.
3. **Metadata leaks from the file:** titles, item types and timestamps are encrypted, row IDs are random, and payloads are padded to size buckets.
4. **Someone seeing the screen:** **since A21 this exists only while security is on, and only if the person switched screenshot protection on (it is off by default).** Then Cipherleaf's windows are excluded from screenshots and screen sharing. With security off no window is protected. The lock screen of a protected vault is hidden from screenshots only when the app starts; after a lock during the session it follows the saved setting (see P21). KeePassXC blocks screen capture by default too, and masks passwords until revealed.
5. **Clipboard leaks:** handled by KeePassXC, which clears copied passwords after a delay (preset to 20 s). **Between A18 and A22 this was not fully true:** a Copy button beside the suggested passphrase put it on the clipboard and Cipherleaf did not clear it. **Removed in A22:** there is no suggested passphrase and no such Copy button any more, so Cipherleaf itself puts no secret on the clipboard. (Windows clipboard history (Win+V) or a cloud clipboard can still keep anything a person copies themselves, or copies from KeePassXC.)
6. **An unattended unlocked PC:** **since A21 only with security on.** An open vault never locks (the idle monitor skips it and `lock()` ignores everything except quit and restore). With security on, Cipherleaf auto-locks on idle (default 5 min), Win+L, sleep or hibernate, removal of the drive, optionally on minimize, and on closing the app. When Cipherleaf locks, it first asks every window to save its pending edits (waiting at most 2 seconds, then locking anyway), then hides KeePassXC, closes sticky notes and sends the window back to the lock screen, and only then makes the backup and wipes the session from memory. **Since A19 the lock also copies the encrypted passwords file** (when it changed) into `data/backups/`, after the vault's own backup and before KeePassXC is asked to lock; an error there never blocks the lock. It also asks a running KeePassXC to lock (`--lock`), even if Cipherleaf did not start it (A17). KeePassXC has its own idle and screen-lock timers (preset: 5 min and on).
7. **Password guessing in the app:** (a protected vault only) each attempt costs a full Argon2id run, and after 3 failures waits grow from 2 s up to 60 s.
8. **Malicious pasted content:** only PNG, JPEG, GIF and WebP images (checked by their bytes), at most 25 MB; no remote loads; links open only as http(s), with Ctrl+click.
9. **Network privacy:** Cipherleaf's own code makes no connections (WebView2, which draws the window, does contact Microsoft addresses at startup; see P5). KeePassXC's update checks, icon downloads, browser integration, SSH agent and Secret Service are preset off.
10. **Traces on the host PC:** everything, including the WebView2 profile and KeePassXC's settings (`data/keepassxc/`), lives in the app's `data` folder.
11. **A swapped or tampered KeePassXC:** Cipherleaf refuses to start an executable whose SHA-256 doesn't match the verified 2.8.0 release.

## Out of scope (not defended)

- Malware, keyloggers, screen scrapers, or an administrator-level compromise on the PC, while unlocked or while the password is typed.
- A tampered `Cipherleaf.exe`, for example one replaced on the USB stick. The app doesn't verify itself, and the exe is unsigned. A tampered KeePassXC is caught only if its `KeePassXC.exe` changes; its DLLs aren't hash-checked.
- The security of KeePassXC itself, including its file format, its handling of memory and its update cadence. KeePassXC isn't part of Cipherleaf's code or review.
- Reading memory while unlocked. Hibernation can also write unlocked data to `hiberfil.sys` before the app locks on resume, and memory isn't protected from the page file.
- Restoring an entire older copy of the vault, which can't be detected offline. Since A18 the owner can do this on purpose with "Restore from a backup"; the app verifies the backup's own password and records, but cannot know whether it is the newest copy. The same holds for the passwords file (A19): a restore puts an older file in place, and the app cannot know whether it is a good database or the newest one.
- A forgotten master password or a lost required keyfile. Recovery is impossible by design.
- **Confidentiality of notes while security is off (A21).** An open vault is encrypted with a public key. Anyone with the file and a copy of Cipherleaf can read it.

## Known limitations

### A21: optional security and Passwords

- **Security off is not confidentiality (A21).** With security off the notes are in the encrypted format, but the key is built into Cipherleaf and public. Anyone who has `vault.clf` or a backup and a copy of Cipherleaf can read the notes. Settings and the README say this in plain words, and since A23 Home shows a one-time dismissible note and the page bar says "Saved on this drive" instead of "Saved & encrypted" while security is off.
- **A protected `vault.clf` can be replaced by an open one (A21).** Someone with write access to `data\` can put an open vault in place of a protected one. Cipherleaf then opens with no prompt and shows empty or different notes. The same access already allows replacing the exe, and the missing prompt is visible. Not defended.
- **Earlier open backups and `restore-undo-*.clf` files stay readable by anyone (A21).** Turning security on offers to delete earlier automatic backups (`data/backups/vault-*.clf`) whose header says open, and their `-journal` files, after a fresh protected backup (default on). It never deletes `restore-undo-*.clf` files, because they hold notes that exist nowhere else; the person removes them by hand. Manual exports made with "Save a backup copy" are never touched. Deleted SQLite journal data may linger on disk. After security is turned off, older protected backups still need their own password and cannot be opened with the new open file. Changing the master password while security is on only re-wraps the header, so older backups still open with the old password (existing limit).
- **Restoring an open backup onto a protected vault turns security off, after a confirmation (A21).** A backup made with security off is restored with no password (its key is built in). If the vault has a master password, `restore_vault` is refused with an error starting "SECURITY_OFF:" until the person confirms. The UI shows a checkbox and sends `allowSecurityOff`. The confirmation is only a UI gate: a script injected into the UI could pass it. Known limit.
- **Screenshot protection and auto-lock exist only while security is on (A21).** With security off there is neither. The lock screen of a protected vault is hidden from screenshots only when the app starts (the window is created protected). After a lock during the session it follows the saved screenshot setting (off by default), so it can be captured. Not changed; recorded as a limit.
- **Backups (A23).** Each backup is written to a temp file, checked with the session key (every record and attachment is authenticated), synced and renamed; a failed copy never exists under a final name. The newest 10 `vault-<ms>.clf` are kept by modified time (a wrong or future-dated clock cannot push out good copies; the file just written is never deleted), and a separate rotation keeps the newest 5 `vault-predelete-<ms>.clf` made before a notebook or section is deleted (the delete is refused if that backup cannot be made). A vault with security off is also backed up about once an hour while it has unsaved-to-backup changes. A failed backup shows a notice, and a failed backup at quit shows a native message before the app closes (not when the drive was removed). A backup holds the session lock while it runs, so very large vaults (about 1 s per 200 MB in a release build) briefly block other commands. Backups older than a password change still open with the old password.
- **Turning security on or off re-keys the vault (A21, `f9d2676`).** It takes a moment, and large notebooks take longer. A copy made while security was off cannot open data written after security was turned on. Why: the independent review showed that re-wrapping alone would let any earlier open copy open the protected vault, because the data key would be the same. Security can be turned off for a vault with a keyfile; the app now reports the keyfile flag while unlocked.
- **Passwords is independent of security (A21).** KeePassXC relies on its own master password and its own idle lock, whether security is on or off. With Passwords off, KeePassXC commands (including `restore_passwords` and `pick_passwords_backup_file`) are refused, and locks and Quit skip KeePassXC and the passwords-file copies. A quit from the lock screen still makes the last passwords-file copy. For a vault saved before A21 the Passwords switch counts as on if a passwords file or `keepassxc\keepassxc.ini` exists.
- **The new commands are callable by any window (A21):** `enable_security`, `disable_security`, `set_passwords_enabled`, `start_notes`, and `restore_vault` with `allowSecurityOff`. `disable_security` needs the current password. `enable_security` can delete earlier automatic backups that were made with security off, without a confirmation beyond the dialog, and `restore_vault` can lower security once `allowSecurityOff` is passed, so a script injected into the UI could do either while the vault is open. See the paragraph under the trust boundaries.

Fixed in `f9d2676`: the two high issues (the shared data key, now re-keying; keyfile users unable to turn security off), the three medium issues and most of the low ones (the list is in EX-2026-10-23-17). Not changed: the lock screen capture after a lock during the session (documented above). Cosmetic: the Turn off security dialog shows two eye icons in its password box (the app's and the browser engine's).

### A20: Start over

- **After Start over, the new vault's automatic backups share `data\backups\` with the old vault's** (the newest 10 `vault-*.clf` are kept, so the old vault's copies are rotated out after 10 more locks, and the restore list shows both). The `set-aside-*.clf` file itself is never rotated. `start_over` needs no password: whoever can use the PC while the vault is locked can already rename `vault.clf` by hand, but "Start over" makes it a few clicks, so the owner may find a vault they can't open. Nothing becomes readable and nothing is lost.
- **`set-aside-*.clf` files (Start over) also open with the OLD password and keyfile,** pile up like the undo files, and are removed by hand.

### Earlier limits (A1 to A19)

- **A crash or power loss in the middle of a restore (A18).** A restore renames the live vault to `restore-undo-<number>.clf` and then renames the verified copy (`restore-check.tmp`) to `vault.clf`. If the PC loses power between the two renames, there is no `vault.clf`: the old vault is in the `restore-undo` file and the verified copy is in `restore-check.tmp`. Since A21 the app then shows the "No notes found here" screen (Restore or Start new notes), not "Create your vault". There is no automatic recovery yet.
- **`restore-undo-*.clf` files open with the OLD password and keyfile (A18).** They are never deleted or rotated by the app, so they pile up; the owner removes them by hand. Restoring a backup also brings back the password that backup had, which matters if the password was changed because it leaked.
- **The suggested passphrase was not cleared from the clipboard (A18). Removed in A22:** the suggested passphrase and its Copy button no longer exist, so this limit no longer applies. (Kept as history: between A18 and A22, after Copy in the first-run screen and later in the Turn on security dialog, Windows clipboard history or a cloud clipboard could keep the passphrase.)
- **The picked backup path stays valid (A18)** until the next pick or a successful restore, so a wrong password can be retried without choosing the file again.
- **A late save from the old window (A18).** A delayed save from the window of the old vault could in theory reach the restored vault in the 1.2 seconds before the screen reloads (small; the restore dialog blocks input).
- **`lock()` is not a barrier against another lock still writing its backup (A18).** A restore started at that moment fails cleanly with the plain "file is in use" message.
- **Any window can call `start_over` (A20),** but it refuses while the vault is unlocked, and sticky-note windows exist only while unlocked.
- **Any window can call `restore_vault` (A18),** with no re-authentication of the current vault. The Content Security Policy and the picked-path rule are the defenses.
- **Hostile `.clf` files are parsed by SQLite (A18).** Only after the copy, with the restore-only Argon2 limits (memory up to 1 GiB, passes up to 10, lanes up to 16, checked before any Argon2 work) and a 2 GiB size limit.
- **A save that hangs is dropped (A17).** If a window can't finish its save within 2 seconds (for example a USB drive that stopped answering), the lock goes ahead and that last edit is lost. There is no automatic timed retry.
- **Lock after sleep or a screen lock may take up to 2 seconds** while the windows are asked to save (a window that is reloading doesn't answer).
- **Up to 10 copies of the encrypted passwords file sit in `data/backups/` (A19).** They open with the KeePassXC master password the file had when the copy was made, so an old master password stays usable through an old copy (as with the vault backups). They are rotated by modified time, not by age. The backups still cover only `vault.clf` and the passwords file, nothing else.
- **`passwords-undo-*.kdbx` files are never deleted or rotated (A19).** They pile up; the owner removes them by hand. They open with the master password the replaced file had.
- **A crash or power loss between the two renames of a passwords restore (A19)** leaves no live database: the old one is in `passwords-undo-*.kdbx` and the new one in `passwords-restore-check.tmp`. There is no recovery notice yet.
- **A backup copy of the passwords file is checked only for its KeePass signature and size (A19).** The restore asks for no password, so Cipherleaf cannot tell whether a copy is a good database; the dialog says it opens with the KeePassXC master password it had when it was made.
- **The torn-copy check relies on the file system's modified-time resolution (A19).** It compares size and modified time before and after the copy. A save that finishes in the same tick with the same size would not be noticed (the signature check still applies).
- **Any window can call `restore_passwords` (A19),** gated only by the unlocked state and the bare-name / picked-path rules, with no re-authentication. The Content Security Policy is the other defense.
- **A hand-placed file named exactly `passwords-<digits>.kdbx` in `data/backups/` is treated as a backup copy (A19)** and can be rotated away (documented in a code comment).
- **After a cancelled Quit, KeePassXC stays as its own window next to a locked Cipherleaf (A19).** It may be unlocked or waiting for an answer, and the `--lock` request may be blocked by its own save question. So the promise that KeePassXC hides when Cipherleaf locks does not hold in that case.
- **Quit can take up to 10 seconds (A19)** when KeePassXC is slow to close. Quit while KeePassXC lives in the system tray or hidden, and when Windows logs off or shuts down, was not tested. (Before A19, Quit force-ended KeePassXC after 3 seconds, which could interrupt a save; that no longer happens.)
- **A pasted picture can be removed by the cleanup** if another page is deleted within the save delay of the page that holds the picture (plausible, low frequency; not fixed, see the backlog in [EX-13](execution/2026-10-23-lock-and-data-loss-fixes.md#findings-not-fixed-backlog)).
- **A2 (pending owner decision):** restoring an older copy of a single record isn't detected, although the plan promises it.
- **A1:** Argon2 settings are fixed rather than tuned per PC.
- After a password change, **older backups** in `data/backups/` still open with the old password and keyfile (the Change password dialog and the README say so). Since A23 records written after the change cannot be opened with the old password, even with an old backup's header (before A23 they could).
- The failed-attempt delay is in memory, so it **resets when the app restarts**.
- **Visible metadata:** the file is recognizably SQLite. Record and attachment counts, approximate sizes, the Argon2 settings, the vault ID and whether a keyfile is required are all visible.
- **Appearance settings in plaintext:** theme, accent, font, and layout choices such as the sidebar width, in the WebView2 storage inside `data/webview/`.
- **Two master passwords:** Cipherleaf and KeePassXC are unlocked separately.
- **KeePassXC needs the Microsoft Visual C++ 2015–2022 x64 runtime** installed on the PC. The V1.0 portable ZIP carries Microsoft's installer `vc_redist.x64.exe` inside the `KeePassXC\` folder (it is KeePassXC's upstream package content); nothing runs it automatically. `Cipherleaf.exe` itself does not import the runtime DLLs (read from its import table).
- **Cipherleaf's lock-when-unplugged and screenshot blocking don't cover KeePassXC's window.** KeePassXC has its own protections.
- **KeePassXC may remember recent file paths** in its settings (the preset turns that off; the owner can change it).
- **Bundled copy must be kept updated:** 2.8.0 fixed several security issues, and later releases may too. 2.7.12 is the fallback if 2.8.0 shows problems.
- **Databases made with `keepassxc-cli` default to AES-KDF**, which is weaker than Argon2. Create the database in KeePassXC's own wizard and choose Argon2id.
- **The embedded KeePassXC is an overlay, not a true child window (A10).** Windows refused to make it a child, and WebView2 draws over child windows. Web content drawn by Cipherleaf (such as the command palette) can't appear on top of it, so it hides while the palette is open. If Cipherleaf crashes, KeePassXC keeps running as its own window (with its own idle lock).
- **Window-style changes to KeePassXC.** Cipherleaf removes its title bar and borders while embedded and restores them on detach. This changes only how the window looks and is positioned; KeePassXC's code and settings are untouched.
- **Licensing (A9 Q5):** KeePassXC is GPL v2 or v3. The release must include its license files and source link; the owner confirms this before distributing Cipherleaf. The owner decided on 2026-10-22 23:14 UTC that the build stays private (owner, close people and friends); each copy carries the license files, the source and the README.

## Cryptography (as implemented)

- **Password handling:** the password is Unicode-normalized (NFC), then stretched with Argon2id v1.3 (256 MiB memory, 3 passes, 4 lanes, 32-byte random salt).
- **Open vault (A21):** header flag `FLAG_OPEN` (bit 1 of the flags byte, authenticated like the rest of the header). The data key is wrapped under a built-in, public password with cheap Argon2 settings (8 MiB, 1 pass, 1 lane), because there is nothing to guess. Records, padding and tamper checks are unchanged. Turning security on or off re-keys the vault: a fresh data key and vault id, with every record and attachment re-encrypted in one transaction (all or nothing), then the new header. Since A23, changing the master password while security is on re-keys the vault the same way (before A23 it only re-wrapped the header, which kept the data key). A Cipherleaf older than A21 refuses such a file as damaged.
- **Key-encryption key:** HKDF-SHA256 over the Argon2 output, plus the keyfile's SHA-256 when a keyfile is used.
- **Data key:** 256 bits from the OS random generator, wrapped with XChaCha20-Poly1305. The first 67 header bytes are authenticated alongside it.
- **Records:** XChaCha20-Poly1305 with a fresh random 24-byte nonce on every write. The authenticated data is `"cipherleaf"`, the format version, the vault ID, the table tag and the row ID.
- **Padding:** plaintext is padded to buckets of 256 B (up to 4 KiB), 4 KiB (up to 64 KiB) and 64 KiB above that.
- **Header limits:** Argon2 settings read from a file are bounds-checked: memory 8 KiB to 4 GiB, passes 1–64, lanes 1–64.
- **Storage:** SQLite with `secure_delete=ON`, `journal_mode=DELETE` and `synchronous=FULL`.
