# Security design: Cipherleaf

This record states what Cipherleaf protects, where its trust boundaries are, what it promises, and its known limitations. It describes the code as of amendments A9 to A24 (A24, from 2026-10-27, removed KeePassXC and the Passwords feature, see the A24 section under the known limitations; A23 is the V1.0.1 audit fixes, noted where they changed something; A22, from 2026-10-23, removed the suggested passphrase, its Copy button and the `eff-wordlist` crate, so that clipboard limit no longer applies; the credits work of the same day added `THIRD-PARTY-NOTICES.md` and no new promise; A20, Start over, merged into `main` on 2026-10-23 and not yet in a portable build; A21, the latest before A22, is from 2026-10-23: Cipherleaf is a notes app first, security (master password, auto-lock, screenshot protection) and Passwords (KeePassXC) are optional switches, commits `84b281d` and `0929ae5`, then the review fixes in `f9d2676`, which added promises P20 and P21, changed P7, P8, P11 and P18, and added the A21 limits below; A21 is built and tested on the owner's PC on throwaway data (draft [PR #3](https://github.com/AbyssWatcher2/CipherLeaf/pull/3), tested at head `5ef5b07`), not yet accepted; A19, commit `442036e`, added copies and a restore of the encrypted KeePassXC passwords file and a Quit that never force-ends KeePassXC, promise P18, and changed P11 and threat 6; A18, commit `1273093`, added the readable first-run passphrase and restore from backup, promise P17 and a clipboard copy of the suggested passphrase (removed again in A22); A17, commit `dc95fd3`, changed the lock sequence and added promise P16): Cipherleaf's own vault holds notes, sticky notes and settings. Since A24 Cipherleaf has no passwords feature (from A9 to A23, passwords were kept in the bundled KeePassXC 2.8.0, shown inside the Cipherleaf window). **Since A21 the master password is optional.** A vault can be open (no password, not confidential) or protected (master password); the person can switch between them at any time. Each promise is a claim to verify, not a guarantee. Update this file when a promise, boundary or limitation changes.

A dependency scan, a plaintext search or a passing test can support one specific claim. None of them shows on its own that the app is secure.

## What it protects

- **Cipherleaf vault contents:** notes and pages, sticky notes, pasted images and settings. **Since A21 this protection is confidentiality only while security is on.** With security off the contents are still in the encrypted, tamper-checked format, but the key is public, so they are not private (see the A21 limits below). Since A23 the screens do not call the notes "encrypted" while security is off.
- **Cipherleaf keys and credentials:** the master password, the optional keyfile, and the 256-bit data key that encrypts everything.
- **Passwords: removed in A24.** From A9 to A23 the bundled KeePassXC kept passwords in `data/passwords.kdbx`, and from A19 Cipherleaf copied that encrypted file on each lock and could restore it. Since A24 Cipherleaf does not start KeePassXC and does not open, copy, back up or restore `data/passwords.kdbx` or its copies. An existing file is left as it is: it keeps KeePassXC's own encryption, and Cipherleaf no longer protects or backs it up.

## Trust boundaries

| Zone | Trust | What crosses the boundary |
|---|---|---|
| Disk / USB stick (`data/vault.clf`, `data/backups/`) | **Untrusted.** Anyone may copy or modify these files. | Only ciphertext (an authenticated header and records for Cipherleaf's vault). Since A24 Cipherleaf does not read or write the KeePassXC files an earlier version left in `data/`. |
| Rust core (in-process) | Trusted. The only holder of Cipherleaf's keys. | — |
| UI (WebView2, same process) | Trusted to display data; never receives keys. | Decrypted note and sticky-note content it shows; the Cipherleaf master password while typing it |
| **Bundled KeePassXC (A9): removed in A24** | Not applicable. | Nothing. Cipherleaf no longer starts, shows, locks or closes KeePassXC. |
| Windows (clipboard, screen capture, other processes) | Partly trusted | Window pixels of Cipherleaf (capture-protected while security and the setting are on). Cipherleaf writes to the clipboard only when the calculator's Copy button is pressed (P15). |
| Network | Untrusted; **unused by Cipherleaf's own code** | Cipherleaf's code has no network code. The Microsoft WebView2 component that draws the window was seen making outbound HTTPS connections at startup (live check 2026-10-23; contents not captured, address owner inferred). |

Every app command is callable by any Cipherleaf window. So a script injected into the UI could read the vault while it's unlocked. Since A18 this includes `restore_vault`, which replaces the vault file and needs no re-authentication of the current vault (it needs the password of the backup being restored). The picked-path rule (see P17) limits what such a script could point it at. From A19 to A23 this also included `restore_passwords`, which replaced the KeePassXC passwords file; it was removed in A24. **Since A21 this also includes `enable_security`, `disable_security` and `start_notes`** (and, until A24 removed it, `set_passwords_enabled`). `disable_security` needs the current password (and keyfile) and is rate-limited like unlock. It is not the only way to lower security. `restore_vault` can turn security off for a vault that has a master password, when it is given a backup that was made with security off and `allowSecurityOff` is true. The checkbox in the restore dialog is only a UI gate, so a script injected into the UI could pass that value. `enable_security` needs no extra confirmation beyond the dialog in the UI and can delete earlier automatic backups that were made with security off (`remove_unprotected_copies`). A script injected into the UI could call it while the vault is open, and it would set a password the owner does not know. Both are callable by any window and are recorded as limits. `start_notes` creates a new open vault only when none exists. The mitigations are a strict Content Security Policy (no remote scripts, styles, images or connections), no remote content, image sniffing, and rejecting SVG.

## Threats it's designed to resist

1. **Stolen or copied vault or backup (offline guessing):** Argon2id with high memory cost, an optional keyfile, and a master-password rule (at least 10 characters and a zxcvbn score of 3 or more).
2. **Tampering with the vault file:** every record and the header are authenticated. Changed bytes, swapped records, records moved between tables or vaults, and edited key-derivation settings are all detected.
3. **Metadata leaks from the file:** titles, item types and timestamps are encrypted, row IDs are random, and payloads are padded to size buckets.
4. **Someone seeing the screen:** **since A21 this exists only while security is on, and only if the person switched screenshot protection on (it is off by default).** Then Cipherleaf's windows are excluded from screenshots and screen sharing. With security off no window is protected. The lock screen of a protected vault is hidden from screenshots only when the app starts; after a lock during the session it follows the saved setting (see P21).
5. **Clipboard leaks:** Cipherleaf itself puts no secret on the clipboard. Its only clipboard write is the calculator's Copy button, which writes the displayed result (P15). From A9 to A23, passwords copied from KeePassXC were handled by KeePassXC, which cleared them after a delay (preset to 20 s); since A24 there is no KeePassXC in Cipherleaf. **Between A18 and A22 this was not fully true:** a Copy button beside the suggested passphrase put it on the clipboard and Cipherleaf did not clear it. **Removed in A22:** there is no suggested passphrase and no such Copy button any more. (Windows clipboard history (Win+V) or a cloud clipboard can still keep anything a person copies themselves.)
6. **An unattended unlocked PC:** **since A21 only with security on.** An open vault never locks (the idle monitor skips it and `lock()` ignores everything except quit and restore). With security on, Cipherleaf auto-locks on idle (default 5 min), Win+L, sleep or hibernate, removal of the drive, optionally on minimize, and on closing the app. When Cipherleaf locks, it first asks every window to save its pending edits (waiting at most 2 seconds, then locking anyway), then closes sticky notes and sends the window back to the lock screen, and only then makes the backup and wipes the session from memory. From A19 to A23 the lock also copied the encrypted KeePassXC passwords file into `data/backups/` and asked a running KeePassXC to lock (`--lock`); since A24 it does neither.
7. **Password guessing in the app:** (a protected vault only) each attempt costs a full Argon2id run, and after 3 failures waits grow from 2 s up to 60 s.
8. **Malicious pasted content:** only PNG, JPEG, GIF and WebP images (checked by their bytes), at most 25 MB; no remote loads; links open only as http(s), with Ctrl+click.
9. **Network privacy:** Cipherleaf's own code makes no connections (WebView2, which draws the window, does contact Microsoft addresses at startup; see P5).
10. **Traces on the host PC:** everything, including the WebView2 profile, lives in the app's `data` folder. Since A24 Cipherleaf no longer creates `data/keepassxc/`.
11. **A swapped or tampered KeePassXC: removed in A24.** Cipherleaf no longer starts KeePassXC, so there is no hash check any more. (From A9 to A23, Cipherleaf refused to start a `KeePassXC.exe` whose SHA-256 didn't match the verified 2.8.0 release.)

## Out of scope (not defended)

- Malware, keyloggers, screen scrapers, or an administrator-level compromise on the PC, while unlocked or while the password is typed.
- A tampered `Cipherleaf.exe`, for example one replaced on the USB stick. The app doesn't verify itself, and the exe is unsigned.
- Reading memory while unlocked. Hibernation can also write unlocked data to `hiberfil.sys` before the app locks on resume, and memory isn't protected from the page file.
- Restoring an entire older copy of the vault, which can't be detected offline. Since A18 the owner can do this on purpose with "Restore from a backup"; the app verifies the backup's own password and records, but cannot know whether it is the newest copy.
- A forgotten master password or a lost required keyfile. Recovery is impossible by design.
- **Confidentiality of notes while security is off (A21).** An open vault is encrypted with a public key. Anyone with the file and a copy of Cipherleaf can read it.

## Known limitations

### A24: KeePassXC removed (2026-10-27)

- **What was removed.** The bundled KeePassXC 2.8.0 support: starting it after a hash check, the in-window overlay, the Passwords switch (`set_passwords_enabled`, the `passwordsEnabled` setting), the Passwords sidebar item, `Ctrl+2` and its command palette entry, the copies of the passwords file made on lock and their restore (`list_password_backups`, `pick_passwords_backup_file`, `restore_passwords`), and the Quit that waited up to 10 seconds for KeePassXC to close. Promises P6, P11 and P18 and threat 11 are marked removed; their numbers are kept. The `CIPHERLEAF_KEEPASSXC` environment variable is no longer read. No Rust or npm dependency changed.
- **Quit.** Quit now locks (the windows save their pending edits, then the vault backup is made) and exits. It is no longer cancelled, and a failed backup at quit still shows a native message first.
- **Existing passwords files are left alone and are no longer backed up.** `data/passwords.kdbx`, `data/keepassxc/` (KeePassXC's settings, which may hold recent file paths), the copies `data/backups/passwords-*.kdbx` and any `passwords-undo-*.kdbx` files stay on disk as they are. Cipherleaf does not read, copy, rotate, restore or delete them, and turning security on does not delete them (it deletes only `vault-*.clf` backups). They keep KeePassXC's own encryption and open in KeePassXC itself. Each copy still opens with the KeePassXC master password the file had when the copy was made, so an old KeePassXC master password stays usable through an old copy. The owner backs up or removes these files by hand.
- **Older vaults.** A vault saved with the `passwordsEnabled` setting still loads; the field is ignored.
- **Visual C++ runtime.** It was needed only by KeePassXC, so the README no longer lists it. `Cipherleaf.exe` itself does not import the runtime DLLs (read from its import table; not tested on a PC without the runtime).
- **Not changed by A24:** vault encryption, security on and off, auto-lock, screenshot protection, the vault backups and their restore, and Start over.

### A21: optional security and Passwords

- **Security off is not confidentiality (A21).** With security off the notes are in the encrypted format, but the key is built into Cipherleaf and public. Anyone who has `vault.clf` or a backup and a copy of Cipherleaf can read the notes. Settings and the README say this in plain words, and since A23 Home shows a one-time dismissible note and the page bar says "Saved on this drive" instead of "Saved & encrypted" while security is off.
- **A protected `vault.clf` can be replaced by an open one (A21).** Someone with write access to `data\` can put an open vault in place of a protected one. Cipherleaf then opens with no prompt and shows empty or different notes. The same access already allows replacing the exe, and the missing prompt is visible. Not defended.
- **Earlier open backups and `restore-undo-*.clf` files stay readable by anyone (A21).** Turning security on offers to delete earlier automatic backups (`data/backups/vault-*.clf`) whose header says open, and their `-journal` files, after a fresh protected backup (default on). It never deletes `restore-undo-*.clf` files, because they hold notes that exist nowhere else; the person removes them by hand. Manual exports made with "Save a backup copy" are never touched. Deleted SQLite journal data may linger on disk. After security is turned off, older protected backups still need their own password and cannot be opened with the new open file. Changing the master password while security is on re-keys the vault (A23), and older backups still open with the old password (existing limit).
- **Restoring an open backup onto a protected vault turns security off, after a confirmation (A21).** A backup made with security off is restored with no password (its key is built in). If the vault has a master password, `restore_vault` is refused with an error starting "SECURITY_OFF:" until the person confirms. The UI shows a checkbox and sends `allowSecurityOff`. The confirmation is only a UI gate: a script injected into the UI could pass it. Known limit.
- **Screenshot protection and auto-lock exist only while security is on (A21).** With security off there is neither. The lock screen of a protected vault is hidden from screenshots only when the app starts (the window is created protected). After a lock during the session it follows the saved screenshot setting (off by default), so it can be captured. Not changed; recorded as a limit.
- **Backups (A23).** Each backup is written to a temp file, checked with the session key (every record and attachment is authenticated), synced and renamed; a failed copy never exists under a final name. The newest 10 `vault-<ms>.clf` (made at lock and quit) are kept by modified time (a wrong or future-dated clock cannot push out good copies; the file just written is never deleted). Two separate rotations keep the newest 3 `vault-hourly-<ms>.clf` (an open vault, security off, is also backed up about once an hour while it has changes since the last hourly copy, and only after 30 seconds without keyboard or mouse input, or 90 minutes overdue; a failed hourly backup is retried after 5 minutes, then 15, then hourly, and is announced on the first failure and again from the third on, so a drive that stays broken is not hammered) and the newest 5 `vault-predelete-<ms>.clf` made before a notebook or section is deleted (the delete is refused if that backup cannot be made). So hourly copies never push out the older ordinary backups. Turning security on with the default tick deletes every unprotected backup, safety copies and hourly copies included (the dialog and README say so), so a notebook deleted before that cannot be brought back from its safety copy. A failed backup shows a notice that reassures ("still saved") only when the cause is the place the copy goes to (a full drive, a folder that cannot be written); a database or drive error gets a "do not rely on the vault file alone" text instead. A failed backup at quit shows a native message before the app closes (not when the drive was removed). A backup holds the session lock while it runs (about 1 s per 200 MB on an SSD with a release build; a slow USB stick can take many seconds), so it briefly blocks other commands; that is why the hourly one waits for a pause. A backup, a password change and a notebook or section delete fail if any record or attachment in the vault cannot be decrypted (a damaged vault), because the copy is checked in full; restore applies the same all-or-nothing check. With security off the safety and hourly copies keep deleted notes readable by anyone with the folder, like the vault itself. Backups older than a password change still open with the old password.
- **Turning security on or off re-keys the vault (A21, `f9d2676`).** It takes a moment, and large notebooks take longer. A copy made while security was off cannot open data written after security was turned on. Why: the independent review showed that re-wrapping alone would let any earlier open copy open the protected vault, because the data key would be the same. Security can be turned off for a vault with a keyfile; the app now reports the keyfile flag while unlocked.
- **Passwords is independent of security (A21). Removed in A24:** there is no Passwords switch and no KeePassXC any more. (Was: KeePassXC relied on its own master password and idle lock; with Passwords off, its commands were refused and locks and Quit skipped it, except that a quit from the lock screen still made the last passwords-file copy.)
- **The new commands are callable by any window (A21):** `enable_security`, `disable_security`, `start_notes`, and `restore_vault` with `allowSecurityOff` (`set_passwords_enabled` was removed in A24). `disable_security` needs the current password. `enable_security` can delete earlier automatic backups that were made with security off, without a confirmation beyond the dialog, and `restore_vault` can lower security once `allowSecurityOff` is passed, so a script injected into the UI could do either while the vault is open. See the paragraph under the trust boundaries.

Not changed: the lock screen capture after a lock during the session (documented above). ### A20: Start over

- **After Start over, the new vault's automatic backups share `data\backups\` with the old vault's** (the newest 10 `vault-*.clf` are kept, so the old vault's copies are rotated out after 10 more locks, and the restore list shows both). The `set-aside-*.clf` file itself is never rotated. `start_over` needs no password: whoever can use the PC while the vault is locked can already rename `vault.clf` by hand, but "Start over" makes it a few clicks, so the owner may find a vault they can't open. Nothing becomes readable and nothing is lost.
- **`set-aside-*.clf` files (Start over) also open with the OLD password and keyfile,** pile up like the undo files, and are removed by hand.

### Earlier limits (A1 to A19)

- **A crash or power loss in the middle of a restore (A18).** A restore renames the live vault to `restore-undo-<number>.clf` and then renames the verified copy (`restore-check.tmp`) to `vault.clf`. If the PC loses power between the two renames, there is no `vault.clf`: the old vault is in the `restore-undo` file and the verified copy is in `restore-check.tmp`. Since A21 the app then shows the "No notes found here" screen (Restore or Start new notes), not "Create your vault". There is no automatic recovery yet.
- **`restore-undo-*.clf` files open with the OLD password and keyfile (A18).** They are never deleted or rotated by the app, so they pile up; the owner removes them by hand. Restoring a backup also brings back the password that backup had, which matters if the password was changed because it leaked.
- **The suggested passphrase was not cleared from the clipboard (A18). Removed in A22:** the suggested passphrase and its Copy button no longer exist, so this limit no longer applies. (Kept as history: between A18 and A22, after Copy in the first-run screen and later in the Turn on security dialog, Windows clipboard history or a cloud clipboard could keep the passphrase.)
- **The picked backup path stays valid (A18)** until the next pick or a successful restore, so a wrong password can be retried without choosing the file again.
- **A late save from the old window (A18).** A delayed save from the window of the old vault could in theory reach the restored vault in the 1.2 seconds before the screen reloads (small; the restore dialog blocks input).
- **`lock()` is not a barrier against another lock still writing its backup (A18).** A restore started at that moment fails cleanly with the plain "file is in use" message.
- **Any window can call `start_over` (A20),** but it refuses while the vault is unlocked, and sticky-note and calculator windows exist only while unlocked.
- **Calculator history is saved (A24).** Calculations typed into a calculator (amounts, PINs worked out by hand) stay in the vault until Clear is pressed, and are in its backups. They are not searchable. An older Cipherleaf that saves its settings drops the history (nothing else is lost).
- **Recent searches are saved (V1.5.1).** The search box remembers the last five things searched for (each at most 200 characters), so a search term, which can reveal what a note says, stays in the vault until it is forgotten (X on one line, "Clear recent searches") or the vault is restored from an older copy. They are kept in the vault's settings record (encrypted like every record; with security off, readable by anyone with the file, like the notes) and in its backups, and reach the UI only through `search_history`, `add_search_term`, `remove_search_term` and `clear_search_history` (not through `get_settings`; `save_settings` cannot overwrite them). They are wiped from memory when the vault locks. A term is stored only when the person opens a result of that search. An older Notaya that saves its settings drops them.
- **Back / forward history is memory only (V1.5.1).** The list of places visited (page ids, at most 100) lives in the window's memory, is never written to the vault, the disk or the browser storage, and disappears when the window closes or the vault locks. The Backspace and mouse-back keys are handled in the UI only and do no file or network access.
- **`Object.prototype` is no longer frozen (V1.5.1, owner's decision 2026-11-04 23:20:04 UTC, tap on "Turn the freeze off, keep Mermaid").** `freezePrototype` in `tauri.conf.json` (which freezes `Object.prototype` in every frame so a script cannot add or change properties every object inherits) is now `false`. Why: Mermaid's libraries assign properties such as `valueOf` on their own class prototypes, which throws once `Object.prototype` is frozen, so no diagram drew in the real exe (PC round bug BUG-9, 2026-11-04). What is lost: one defense in depth against prototype pollution by a script in the page. What still stands: only the bundled scripts run (the Content-Security-Policy allows no outside, inline or eval script), the page has no network, imports are parsed in the Rust core and sanitized, Mermaid runs in strict mode with a cleaned drawing, and the frontend does not merge untrusted JSON into objects. Restoring the freeze means dropping or patching the libraries that need it.
- **Mermaid diagrams (V1.5.1, built 2026-11-04, not yet accepted; owner approved adding the `mermaid` package 2026-11-04 17:56:54 UTC).** A "Diagram" block keeps Mermaid code in the page (at most 50,000 characters) and the editor draws it to an SVG on this device with `mermaid` 12.2.0 (MIT), loaded only when a diagram is first shown. The code may come from an imported file, so it is treated as hostile: the library runs with `securityLevel: "strict"` (labels escaped, `click` actions and links inert), `startOnLoad: false`, `htmlLabels: false`, `maxTextSize` 50,000, `maxEdges` 500, no error drawing and a 15-second drawing limit; init directives (`%%{...}%%`) and front matter are removed from the code before drawing, so a diagram cannot switch those settings or set its own CSS; the SVG the library returns is parsed and cleaned again (no `script`, `iframe`, `object`, `img`, animation or form elements, no `on...` attributes, links removed, `href` kept only for `#id` references, no `url()` or `@import` pointing outside the drawing) and is added with DOM calls, never as an HTML string. Nothing is fetched (no fonts, icon packs or images) and the Content Security Policy is unchanged (no `unsafe-eval`, no new host); in the built mock page under the same policy as a meta tag no violation was reported, and the shipped chunks contain no `eval` or `new Function` call that runs (a `Function("return this")` fallback in a bundled helper is reached only when `self` is missing). Exports carry the diagram as its code (Word, PDF, HTML, Markdown) with the caption "Mermaid diagram (code)", never as a picture; the plain-text copy holds the code, so search finds it. **Limits:** a very large or slow diagram can still make the window unresponsive for a moment (the 15-second limit stops waiting, not the drawing itself); not tested in the real WebView2 window, only in the mock UI (Chromium) with the policy added as a meta tag.
- **Any window can call `restore_vault` (A18),** with no re-authentication of the current vault. The Content Security Policy and the picked-path rule are the defenses.
- **Hostile `.clf` files are parsed by SQLite (A18).** Only after the copy, with the restore-only Argon2 limits (memory up to 1 GiB, passes up to 10, lanes up to 16, checked before any Argon2 work) and a 2 GiB size limit.
- **A save that hangs is dropped (A17).** If a window can't finish its save within 2 seconds (for example a USB drive that stopped answering), the lock goes ahead and that last edit is lost. There is no automatic timed retry.
- **Lock after sleep or a screen lock may take up to 2 seconds** while the windows are asked to save (a window that is reloading doesn't answer).
- **Removed in A24: the A19 limits on the passwords file and on Quit with KeePassXC.** These were: up to 10 copies of the passwords file in `data/backups/`, `passwords-undo-*.kdbx` files never deleted, a crash between the two renames of a passwords restore, a copy checked only for its signature and size, the torn-copy check, `restore_passwords` callable by any window, a hand-placed `passwords-<digits>.kdbx` treated as a copy, KeePassXC left as its own window after a cancelled Quit, and a Quit that could take up to 10 seconds. Cipherleaf no longer has these features. Files made before A24 stay on disk (see the A24 section).
- **A pasted picture can be removed by the cleanup** if another page is deleted within the save delay of the page that holds the picture (plausible, low frequency; not fixed, see the backlog in [EX-13](execution/2026-10-23-lock-and-data-loss-fixes.md#findings-not-fixed-backlog)).
- **A2 (pending owner decision):** restoring an older copy of a single record isn't detected, although the plan promises it.
- **A1:** Argon2 settings are fixed rather than tuned per PC.
- After a password change, **older backups** in `data/backups/` still open with the old password and keyfile (the Change password dialog and the README say so). Since A23 records written after the change cannot be opened with the old password, even with an old backup's header (before A23 they could).
- The failed-attempt delay is in memory, so it **resets when the app restarts**.
- **Visible metadata:** the file is recognizably SQLite. Record and attachment counts, approximate sizes, the Argon2 settings, the vault ID and whether a keyfile is required are all visible.
- **Appearance settings in plaintext:** theme, accent, font, and layout choices such as the sidebar width, in the WebView2 storage inside `data/webview/`.
- **Removed in A24: the KeePassXC limits.** These were: two master passwords (Cipherleaf and KeePassXC), the Visual C++ runtime that KeePassXC needed, Cipherleaf's lock-when-unplugged and screenshot blocking not covering KeePassXC's window, recent file paths in KeePassXC's settings, keeping the bundled copy updated, databases made with `keepassxc-cli` defaulting to AES-KDF, the overlay window and its window-style changes, and licensing (A9 Q5: KeePassXC is GPL v2 or v3 and its license files and source had to ship with it). Cipherleaf no longer ships or starts KeePassXC.

## Cryptography (as implemented)

- **Password handling:** the password is Unicode-normalized (NFC), then stretched with Argon2id v1.3 (256 MiB memory, 3 passes, 4 lanes, 32-byte random salt).
- **Open vault (A21):** header flag `FLAG_OPEN` (bit 1 of the flags byte, authenticated like the rest of the header). The data key is wrapped under a built-in, public password with cheap Argon2 settings (8 MiB, 1 pass, 1 lane), because there is nothing to guess. Records, padding and tamper checks are unchanged. Turning security on or off re-keys the vault: a fresh data key and vault id, with every record and attachment re-encrypted in one transaction (all or nothing), then the new header. Since A23, changing the master password while security is on re-keys the vault the same way (before A23 it only re-wrapped the header, which kept the data key). A Cipherleaf older than A21 refuses such a file as damaged.
- **Key-encryption key:** HKDF-SHA256 over the Argon2 output, plus the keyfile's SHA-256 when a keyfile is used.
- **Data key:** 256 bits from the OS random generator, wrapped with XChaCha20-Poly1305. The first 67 header bytes are authenticated alongside it.
- **Records:** XChaCha20-Poly1305 with a fresh random 24-byte nonce on every write. The authenticated data is `"cipherleaf"`, the format version, the vault ID, the table tag and the row ID.
- **Padding:** plaintext is padded to buckets of 256 B (up to 4 KiB), 4 KiB (up to 64 KiB) and 64 KiB above that.
- **Header limits:** Argon2 settings read from a file are bounds-checked: memory 8 KiB to 4 GiB, passes 1–64, lanes 1–64.
- **Storage:** SQLite with `secure_delete=ON`, `journal_mode=DELETE` and `synchronous=FULL`.
