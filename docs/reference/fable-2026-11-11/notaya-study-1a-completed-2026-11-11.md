## 1. Answer in plain words

**The recommendation.** Before 1.6 is released, give Notaya's storage a proper way to grow: raise the format number once, and make 1.6 the first version that can meet content from a newer Notaya without breaking or damaging it. Build everything after that (receiving Notion hubs, databases, links to blocks, the AI door) on three fixed ideas:

1. **Every thing has one permanent id.** Pages, rows, blocks, properties and views are found by id, never by title or position. Renaming, moving or having two pages with the same title can then never break a link. A copy always gets new ids.
2. **Every received thing remembers where it came from.** Its Notion id, which hand-over it arrived in and when. That is what later lets Notaya update a hub in place instead of making twins.
3. **Nothing disappears quietly.** What Notaya cannot show yet is kept exactly, in its place, behind a small placeholder, and is listed in a report with the reason and whether it can be got back. "Unknown" is an allowed answer.

**Why now.** Reading the code showed that today's 1.6 keeps the old format number, so the released 1.5.1 would open a 1.6 vault and could damage it without any warning: history and the activity log become unreadable after a password change, pictures used only in new places can be deleted, source ids are lost. This is derived from the code and was not tried on a PC. The format number is the only guard that old versions obey.

**What this enables.** Safe upgrades with a verified copy first; older versions that say "read only" instead of failing; links that survive renames and duplicate titles; rows that are real pages; receiving the same hub again as an update; honest reports of what was and was not captured, limited to what was actually handed over.

**What this study does not decide.** How changes are checked and applied, permissions, the AI's tools, undo and the receive steps (study 1b). Speed and loading on large hubs (study 2). Which database and page features to build (studies 3 and 4). The twelve decisions in section 12 are yours.

**What stays irreversible.** After an upgrade, older Notaya versions cannot open the vault; the only way back is the copy made just before, losing later work. Deleting for good, emptying the bin, clearing the activity log and automatic thinning of old history cannot be undone. There is no universal undo: each such step either has a named way back or asks first and says what will be gone (table in 6.6).

**How sure this is.** Facts about today's code were read at commit 9977e72 and are marked VERIFIED with file and lines. Nothing was built, run or tested. Open unknowns are listed in the checkpoint and in section 13.

## 3. Today's model, verified or UNKNOWN

Everything here was read at `9977e72` (merged, unaccepted 1.6 code) unless marked. File and line references are in the working log (section 13).

**3.1 Items and kinds.** Every stored thing is one encrypted record holding one `Item`, a tagged list of seven kinds: notebook, section, page, sticky, settings, database, row [VERIFIED: model.rs:36-48]. Three properties of this design decide most of this study:
- *An unknown kind breaks the whole vault.* At unlock every record is decrypted and parsed; one record that does not parse makes the unlock fail as "damaged" [VERIFIED: vault/mod.rs:239-248]. There is no fallback kind. The same holds one level down: property kinds and view kinds are closed lists inside the database record [VERIFIED: database/types.rs:43-69, 259-267]. This is what happened when databases arrived in V1.5.0: older versions report such a vault as damaged [REPORTED: security-design P27].
- *An unknown field is silently dropped.* Items ignore fields they do not know when reading and do not write them back. So an older version that re-saves an item removes newer fields from it without any message [VERIFIED: no catch-all field on any item; grep].
- *Everything is in memory.* All items are loaded at unlock; pictures, history bodies and files are read on demand [VERIFIED: vault/mod.rs:239-258].

**3.2 Pages and the page document.** A page stores its body as editor JSON text plus a plain-text copy for search [VERIFIED: model.rs:96-124]. A database row is a page-as-record: one title, one body, one set of cell values, one order number [VERIFIED: database/types.rs:480-513]. The document schema is written down twice by hand, once in the editor and once in Rust [VERIFIED: extensions.ts:28-33; blocks/ids.rs:9-36], plus a third closed list in the import document model [VERIFIED: importers/doc.rs:81-124]. The Rust validator refuses any node type or attribute outside its lists [VERIFIED: blocks/ops.rs:91-131; attrs.rs:20-86]. Columns, callouts (icon only, no colour), toggles and shelves, page-link blocks, inline database blocks, math, Mermaid, per-block direction (`dir`: ltr, rtl or automatic) and heading anchors already exist. Mentions, callout colour, folding headings, a contents block, file/audio/video cards and block-level link targets do not. Stored strings are kept byte for byte on the Rust write path, with a test for Arabic and invisible direction marks [VERIFIED: blocks/mod.rs:50-64, 96-120]. What an older editor does with a node type it does not know was not established: [UNKNOWN; ASSUMPTION that it may show a reduced or empty page].

**3.3 Identity today.**
- Item ids are 16 random bytes shown as 32 hex characters, the same shape as a Notion id [VERIFIED: model.rs:14-16]. The record's row id must equal the item id [VERIFIED: vault/mod.rs:244-246]. Properties, views and options use the same generator.
- Block ids (`bid`) are 8 random bytes, unique only inside one page; duplicates inside a page are re-issued [VERIFIED: blocks/ids.rs:5-7, 49-66]. A block is therefore addressable only as page id plus block id. An older version drops block ids when it saves a page [REPORTED: 1.6 spec WP-02b], so they are not yet stable across versions.
- References take four forms: a link mark `notaya:page/<pageId>` with an optional heading anchor; a page-link block; an inline database block; relation cells holding row ids [VERIFIED: internalLinks.ts:1-18; more-blocks.ts:48-59; relations.rs:16-24]. A heading without an anchor is addressed by its text, a title-match fallback that exists today [VERIFIED: internalLinks.ts:3-6]. No backlink or reference index was found in what was read; whether one exists elsewhere is [UNKNOWN: not searched beyond the named files].
- Source ids: notebook, section, page, database and row can carry `source: {app, id}` [VERIFIED: model.rs:29-31, 66-97; types.rs:374-376, 480-482]. Only the AI door writes it; the file importer uses Notion ids in memory for matching and then discards them [VERIFIED: ai/dispatch.rs:163-167; notion_db.rs:62-68, 385-399; grep]. Lookup is a scan that can return several items: uniqueness is not enforced [VERIFIED: ai/dispatch.rs:818]. Blocks, views, properties and options have no source id. The tag type refuses unknown fields, so it cannot grow without breaking older versions [VERIFIED: model.rs:30].

**3.4 Format versions and guards.** The header is a fixed 139 bytes with a format name and a version number: "NOTA" version 2 since V1.4.0, "CLF1" version 1 before [VERIFIED: header.rs:3-8, 36-55]. Any other version number is refused with "This vault was made by a newer version of Notaya." and the accepted 1.5.1 has the same check [VERIFIED: header.rs:240-245; 95ca8b2 header.rs:241-243]. Unknown flag bits are reported as damage, so they cannot serve as gentle feature flags [VERIFIED: header.rs:249-251]. The version number is part of what every record is bound to [VERIFIED: vault/mod.rs:73-80]. The one real format change so far (V1.3 to V1.4) re-encrypts everything in a single all-or-nothing transaction after unlock, and a failure leaves the old file readable [VERIFIED: vault/mod.rs:842-887]. There is no schema version inside items, pages or snapshots, and no database-level version number [VERIFIED: store.rs grep].

**3.5 What 1.6 added without changing the version number.** Three tables (history, activity, journal anchor) are created when a file is opened [VERIFIED: store.rs:67-69]; new optional fields (`source`, `trashedAt` on notebooks, sections and stickies, a settings latch, the AI settings); block ids in page content. ## 4. Options

Four ways to shape the content model, identity and format evolution together. All four are [PROPOSAL]; the "today" column of facts behind them is section 3.

**Option A. Keep adding quietly (what 1.6 does).** The version number stays 2. New tables, fields, kinds and node types are added as optional, with a one-time backup and a notice.

**Option B. Versioned and tolerant (recommended).** Three parts: (1) the header version number is raised whenever an older version could damage or misread the vault, so older versions refuse with the sentence they already have; (2) from that point on, every reader keeps what it does not understand (unknown kinds, fields and blocks are preserved untouched and shown as placeholders) and a list of "features in use" inside the vault tells a reader whether it may write, may only read, or must refuse; (3) the page-document schema is defined once, grows only by addition, and every new block type carries a plain-text fallback.

**Option C. Blocks as their own records.** Every block becomes a stored record with a vault-wide id, as Notion does internally. Pages become lists of block ids.

**Option D. Sidecar tables.** Leave version-2 records exactly as they are and put everything new (references, source ids, capability states, new block data) in separate tables that older versions ignore.

| Criterion | A. Add quietly | B. Versioned and tolerant | C. Block records | D. Sidecar tables |
|---|---|---|---|---|
| Native feature growth (1.8, 1.9) | Works until the first clash; each new kind is a silent break | Good: a new kind, field or block follows one checklist | Best in theory (synced blocks, block backlinks) | Poor: page and its extras can drift apart |
| Exactness (text, numbers, Arabic) | As today | As today, plus a rule and tests in the one schema | At risk: every block is rewritten in the move | As today |
| Older version meets a newer vault | Opens it and can destroy data when it writes (section 3.5) | Refuses, or opens read-only, with a clear message | Refuses (must) | Opens it; same write damage as A |
| Migration cost and risk | None now, growing later | Small: one version bump in 1.6, then mostly flags | Very large: every page rewritten, editor boundary redesigned | Medium; two sources of truth |
| Memory and speed | As today | As today; reference lists are small | Worse at unlock: a 240,000-character page becomes thousands of records [ESTIMATE] | Slightly worse |
| Security and privacy | Old versions skip new tables on re-key and purge | New tables and kinds are covered because old versions cannot write | Large new surface to review | Purge and re-key must cover two places |
| Experience | Silent; failures look like "damaged" | Honest messages; placeholders instead of blanks | Unchanged if perfect | Confusing partial pages in old versions |
| Fit with 1b (changes, AI, receive) | Weak: no safe base for re-receive | Strong: ids, origins and states are explicit | Strong but late | Weak |
| Dead-end risk for 2.x | High | Low; does not block C later | Low | High |

**Why B.** It is the smallest change that removes the one verified danger (old versions writing new vaults), and it turns every later format question into a rule instead of a judgement call. C is not rejected for ever: B keeps block ids vault-unique, so a later move to block records would not need new identities. A and D both keep the 1.6 hazard.

## 5. D1 and D2: recommended content model and identity scheme

All of this section is [PROPOSAL] built on the facts of section 3.

### 5.1 D1: content model

**Kinds.** Keep "one item, one encrypted record". A new kind is added only through a written kind checklist, because every one of these is a place where a forgotten kind loses data: where it sits in the tree; bin behaviour; history behaviour; what "delete for good" must remove; which pictures and files it references (for clean-up); its search text; export; whether it can carry an origin; its feature name and class (5.3). REQUIREMENT FOR 1b: the change contract enforces the checklist for every kind.

**Unknown kinds and fields, per released version.**

| Version | Meets something newer | Rule |
|---|---|---|
| V1.3.0 and earlier | Any NOTA file | Cannot open it (already true) |
| V1.4.0 to V1.5.1 | A version-2 vault with 1.6 content | Today: opens, and can damage it by writing. Recommended: 1.6 writes version 3, so these versions refuse with "made by a newer version" |
| 1.6 (not released) | Later content | Make 1.6 the first tolerant reader (below), so every later version can rely on it |
| Every version after | Later content | Tolerant reader plus the feature list |

**The tolerant reader (from the first version-3 release).**
- An item of an unknown kind is loaded as an opaque item: its stored bytes are kept exactly, it is never rewritten, it is counted and named in a "made by a newer Notaya" notice, and it does not appear as editable content.
- Every item and every nested structure that can grow (property, view, option, origin) keeps unknown fields and writes them back unchanged. A field whose truth depends on other data (a cached list, an index) must say what it was derived from, so a reader can tell when it is stale and rebuild it.
- Closed lists inside items (property kind, view kind) get the same treatment: an unknown value is kept and shown as "not available in this version", never a load failure.
- While any unknown kind, or any feature the reader does not know and that is marked "read-only for older versions", is present, the vault opens read-only: no saves, no picture clean-up, no re-key. A feature marked "required" makes the reader refuse after unlock with the feature's name.

**The page document.**
- One schema definition (node types, attributes and their limits, what may contain what, which nodes carry a block id, each node's plain-text fallback) is the single source. The Rust validator, the editor's lists and the import renderer are tested against it, replacing today's three hand-kept lists.
- Additive only. A document schema change may add node types, marks and optional attributes. It never changes the meaning of an existing one. Consequence: every document ever saved, including every history version and bin item, stays valid for every later reader, and no page ever needs rewriting during an upgrade.
- Unknown nodes. A reader that meets a node type it does not know keeps the node's stored JSON untouched and shows a quiet placeholder with the node's fallback text. The placeholder can be moved or deleted as a whole block but not edited. Exports write the fallback text and say what was left out. This must hold in the editor, in the Rust validator (which today refuses the page) and in exports. Until it is built and tested, no new node type may ship without a version bump.
- Every new node type or inline carries its own fallback text (a mention stores the title it showed), used for search, export and placeholders, never for finding the target.

**Exact text and numbers.** No path may normalise, trim, re-order, re-encode or cut a stored string: not the editor, an import, an AI write, a migration or a copy button. Where a limit forces a cut, the item is marked TRANSFORMED and the cut is reported (today's Mermaid and math trims are silent as far as was read). Invisible direction characters, soft line breaks and trailing newlines are content. Numbers that must be exact are stored and compared as decimal text, never as binary floating point; "unknown" is a distinct value from zero and from empty. How cells are stored today was not read: [UNKNOWN], handed to study 3.

**Page-as-record.** A database row is the only holder of its title, body and cells (true in the model today). Views, inline database blocks, link-to-page blocks and mentions are references to it. An imported row page becomes the row and nothing else (A53 item 2). Turning a page into a row or back keeps the same item id, so links survive. REQUIREMENT FOR 1b: conversion and import never leave a second body.

**Typed properties and calculations.** Property, option and view ids are stable and separate from their names (true today). Add an origin to properties, options and views (5.2). A property that came from a calculated source keeps three things apart: the live Notaya definition (may be empty), the source definition as captured (inert text, private), and per row the source result as captured. A captured definition or result is displayed as a stored value with a "not calculated here" state; it becomes a working calculation only when a Notaya formula exists and has been compared with the captured results. Stored snapshots are never silently replaced by recomputation. The detailed design is study 3; 1a fixes only that these slots exist and are distinct.

### 5.2 D2: stable identity

**Item ids.** 128 random bits, shown as 32 hex characters, assigned once, never changed by rename, move, re-parenting, binning, restore or a change of kind, and never derived from a title, a path or a source id. A copy always gets new ids. With random ids, reuse after a purge is not a practical risk; to tell "deleted for good" from "never existed", a content-free tombstone (id, kind, time) is kept for purged items. That marker is a privacy choice for Ahmed (section 12).

**Block ids.** Keep the 1.6 `bid` (16 hex). Add one rule that makes it usable across pages: a move keeps the block id, a copy issues new ones (and re-points links inside the copied material to the copies). Then a block id occurs in at most one live document, and a block is addressed by block id with the page id as a hint. Heading anchors stay readable for ever as an older alias of the heading's block id; new links are written with block ids only. Existing text-addressed heading links (`#t:`) are resolved only when exactly one heading matches, otherwise shown as unresolved; no new ones are written.

**References.** One shape wherever a reference is stored (link mark, mention, page-link block, database block, view link, relation cell, contents entry): target item id; optional block id; optional view id; reference kind; cached label for display. The label is never used to find the target.

**Resolution states.** Resolution is a pure function of the reference and the current vault: *resolved*; *in bin* (the target or an ancestor is binned); *purged* (tombstone exists); *unresolved* (no such id is known). An unresolved or purged reference is shown as such with its cached label and listed in a report. Nothing is ever created to satisfy a reference.

**Origin (source identity).** Replace the bare `{app, id}` tag with an origin record that can grow: app; source id; source kind (page, database, row, block, view, property, option, file); source set (which receive lineage it belongs to, so the three German copies and a deliberate second import stay apart); route (file or AI); source created and edited times where known; first and last received times. Origins go on items, on properties, options and views, and on blocks as a small attribute beside `bid`. Source ids are matched exactly, as opaque text, within one source set.

**The reference index.** Derived data, never the authority. Each item may store the list of references found in its own content together with a stamp of the content it was derived from; the inverse map (backlinks) is built in memory at unlock from those lists. A list whose stamp does not match its content is rebuilt from the content. This avoids parsing every page at unlock (cost to be measured in study 2 [ESTIMATE: tens of megabytes of page JSON for the full workspace]).

**Invariants (what must always hold; how each change keeps them is 1b's work).**
- I1 Every stored reference names its target by id, never by title, path or position.
- I2 An item's id never changes; ids are never reused; a copy never shares an id (item or block) with its original.
- I3 A block id occurs in at most one live document.
- I4 The reference index equals what a full rebuild from content would produce; if they differ, content wins.
- I5 Resolving, showing, exporting or importing a reference never creates an item.
- I6 Within one source set, at most one live or binned item carries a given source id; a second arrival of the same source id is an update or a reported conflict, never a silent twin.
- I7 A history version restored into its page keeps that page's id; block ids in the restored body that now live in another document are re-issued in the restored body.
- I8 Purging an item removes its origin and its stored reference list with it; the tombstone holds no title, text or source id.

## 6. D3: format evolution, migration, recovery and confirmation boundaries

All [PROPOSAL] unless tagged.

### 6.1 What counts as a format change (this settles conflict C3 by rule)

A change to what is stored falls into one of three classes, judged by one question: *what would an older version do to it?*

| Class | Meaning | How older versions are told |
|---|---|---|
| Required | An older version would misread it or damage it | It must refuse to open the vault |
| Read-only | An older version reads it correctly but would damage it by writing (a table its re-key or purge skips, a field whose loss matters) | It may open the vault read-only |
| Optional | An older version can read and write safely because it preserves what it does not know | Nothing; it works |

Older versions can only be told in two ways. Versions up to 1.5.1 understand exactly one signal: the header version number (section 3.4). Versions built with the tolerant reader (5.1) also understand a feature list.

**The feature list.** One small encrypted record in the vault names the features in use, each with its class, plus the version that last wrote the vault. A version adds a feature name the first time it stores that kind of content. A reader checks the list right after unlock.

**Applying the rule.**

| Change | Class for 1.5.1 and older | Class for a tolerant reader |
|---|---|---|
| 1.6: history, activity and anchor tables | Read-only at best; 1.5.1 cannot be told, so it damages them (3.5) | Read-only |
| 1.6: `trashedAt` on notebooks, sections, stickies; source tags; journal latch | Lost on re-save | Optional (preserved) |
| 1.6: block ids | Dropped on save | Optional |
| 1.8: mentions, contents block, file/audio/video cards (new node types) | Required (old validators refuse; old editors unknown) | Optional, through the placeholder and fallback text |
| 1.8: callout colour, folding headings, block-link addresses, origin on blocks (new attributes or address forms) | Dropped or refused | Optional |
| 1.8: columns, per-block direction | No change: both exist in the document today [VERIFIED: section 3.2] | No change |
| 1.9: origins filled by the file importer, sync ledger, saved-view and row-layout data | Lost on re-save | Optional, or Read-only for the ledger |
| 2.1 dashboard kind, 2.3 whiteboard kind | Required (unknown kind breaks unlock) | Read-only (opaque item) |

**Answer to "one combined 1.8 format change or several".** Neither, if 1.6 does the work first. Raise the header version once, in 1.6, together with the tolerant reader and the feature list. After that, 1.8 and 1.9 need no header change at all: their items are optional or read-only features. If Ahmed prefers not to touch 1.6, then exactly one combined header change at the start of 1.8, carrying the tolerant reader, and never several small ones. Both the version plan's list and the Notion board's list are then answered by the table above rather than by picking one of them.

### 6.2 Raising the version number

Records are bound to the version number [VERIFIED: vault/mod.rs:73-80], so a new number means every record is re-sealed. The proven path is the existing re-key: one transaction, all or nothing, new data key and vault id, old file intact on failure [VERIFIED: vault/mod.rs:842-887]. Its cost on a large vault (a 1 GB import, files up to 900 MB each) was not measured: [NOT RUN]. In one SQLite transaction with the current settings the undo journal can grow to about the size of the vault, so free disk of roughly twice the vault plus the backup is needed [ESTIMATE]. If measurement shows this is too slow, a lighter variant (new header, records keep their existing binding) is possible but is a security-design change that needs its own review; it is not recommended without one.

### 6.3 The migration protocol

1. **Preconditions.** The person has unlocked the vault; AI access is disconnected for the duration; free disk is checked; nothing else is saving.
2. **Tell and confirm.** One dialog says what will happen, where the copy goes, and that Notaya 1.5.1 and older will not open these notes afterwards. The person confirms. Cancelling leaves everything as it was, and the vault stays usable read-only in this version until the upgrade is done.
3. **Backup first.** A full copy is written and verified record by record with the existing copy check [VERIFIED: vault/mod.rs:916-930]. It gets a name that says what it is and is never removed automatically. No verified copy, no migration.
4. **One transaction.** Re-seal, write the header and the feature list. Because the document schema grows only by addition, no page, history version or bin item is rewritten.
5. **Verify after.** Re-open the file and check: header; number of rows per table equal to before; every record authenticates; item counts by kind equal; a digest over all decrypted items equal before and after; the journal anchor verifies. Write one activity entry with the counts.
6. **Only then** use new features, and show one line with the backup's location.

Interruptions: a crash or power loss during step 4 is rolled back by SQLite at the next open (the file is still the old format; the upgrade is offered again). A crash between steps 3 and 4 leaves an extra backup and nothing else. REQUIREMENT FOR 1b: lock, quit and auto-lock either wait for step 4 to finish or cancel before it starts; they never interrupt it.

### 6.4 Older content inside a newer vault

- History versions and bin items stay valid for ever under the additive-only rule (5.1).
- The history integrity hash must stop depending on re-writing the parsed body (3.6). New versions hash the stored bytes; the present body shape is frozen as "version 1" and keeps being checked the present way. Until this is done, the snapshot structure cannot change at all.
- A history version restored into a page is checked by the current validator with the tolerant rules, and block ids follow invariant I7.
- Cell values are not in page history today; how a property change is undone is 1b's question (REQUIREMENT FOR 1b in section 9).

### 6.5 Wording (drafts for Ahmed; plain, no blame, always say whether anything changed)

- Upgrade: "Notaya needs to update how your notes are stored. A full copy is saved first, here: <place>. After the update, Notaya 1.5.1 and older cannot open these notes. To go back you would restore that copy and lose anything written after it."
- Older tolerant version, read-only: "These notes were last used with a newer Notaya. You can read them here, but not change them. Nothing was changed."
- Older tolerant version, refused: "These notes use something this version of Notaya does not have (<feature>). Update Notaya to open them. Nothing was changed."
- Versions up to 1.5.1 already say: "This vault was made by a newer version of Notaya." That text cannot be changed any more.
- Unknown block: "This part needs a newer Notaya. It is kept exactly as it is."

### 6.6 What can be undone, and what cannot

| Step | Can it be reversed, and how | What cannot be recovered | Confirmation boundary |
|---|---|---|---|
| Format upgrade, before step 4 | Yes: cancel; nothing was written | Nothing | The upgrade dialog |
| Format upgrade, after step 4 | Only by restoring the pre-upgrade copy with an older Notaya | Everything written after that copy; older versions can no longer open the upgraded file | Same dialog, once, before the backup |
| An older version writing a newer vault (if the number is not raised) | No. Damage is silent: unreadable history and log after a password change, deleted pictures, lost tags | Whatever was damaged | None exists today. Prevented only by the version number |
| Restoring a backup | The replaced vault can be put back once, if the existing restore-undo copy is still there [REPORTED: security-design SF3 names restore-undo backups] | Changes made after the backup that was restored, once that undo copy is gone | The existing restore confirmation |
| Moving to the bin | Yes: restore from the bin | Nothing | None needed |
| Delete for good, empty the bin | No | The item, its history and undo data in this vault. Older backups and exports still hold it; references to it become "purged" | Windows-owned confirmation naming the count and titles (A51) |
| History thinning and the history size cap | No | Old versions that the thinning rules drop | None today: it happens automatically [REPORTED: 1.6 spec WP-04]. Decision for Ahmed |
| Clearing the activity log | No | The cleared entries and their undo data | Typed confirmation (P31, P33) |
| Changing security or password (re-key) | The setting can be changed again; the old key cannot be brought back | Nothing in this vault; older backups keep their old protection | Existing dialogs |
| Deleting a placeholder for an unknown or unsupported block | Yes while page history holds an earlier version | The original, once history is thinned or the page is purged | None beyond normal editing; the placeholder says the original is kept |
| First use of a feature that older versions cannot write | Not in practice | Older tolerant versions become read-only for this vault | One notice with a backup, at first use |

There is no universal undo. The honest promise is: every destructive step either has a named way back with a stated time limit, or asks first and says what will be gone.

## 7. D4: capability-state data model

All [PROPOSAL] unless tagged. This section says what is stored so that Notaya can always answer "what happened to this source element, and can it be got back?". The receive flow, the report screens and who may change these records are 1b's.

### 7.1 Vocabulary (fixed strings; readers keep values they do not know)

| Axis | Values | Meaning |
|---|---|---|
| State of something that is in the vault | SUPPORTED; PARTIALLY SUPPORTED; TRANSFORMED; UNSUPPORTED | Works natively; works with a named gap; kept but changed in a named way (a cut, a colour mapped, an order not kept); kept only as a stored original behind a placeholder |
| Cause, when something is missing or unusable | NOT CAPTURED; DROPPED; STORED BUT UNUSABLE | The route never handed it to Notaya; Notaya received it and did not keep it; Notaya holds it but cannot show or use it yet |
| Recoverability | by a fixed import; by a future feature; irrecoverable; UNKNOWN | Re-receiving the same source with a corrected importer brings it back; the stored original becomes usable when the feature ships; the source no longer holds it or it was never capturable by this route; not established |

UNKNOWN is a legal stored value, not a gap to be filled by a guess. Only the first axis applies to an element that is present; the second applies only when something is missing or unusable.

### 7.2 Where the facts are stored (three levels)

1. **In the page: a stored-original block.** One new node type (working name `sourceBlock`), added under the additive rule of 5.1. It carries: its block id; its origin (5.2); the source element kind as text (for example "synced block", "button", "embed"); a short fallback label; the captured original, either as inert text inside the node (small) or as the id of an encrypted attachment (large); and the state. It is how an UNSUPPORTED or STORED BUT UNUSABLE element keeps its exact position in the page. The original is never executed, fetched or rendered as live content; it is data. A later version that learns the element converts the block in place and keeps the block id, so links to it survive.
2. **On the item: capability notes.** A bounded list on a page, row or database. Each note has: target (the item itself, a block id, a property id or a view id); source element kind; state; cause where it applies; recoverability; a detail code from a growing list (for example "cut at limit", "colour mapped", "order not kept", "result only, definition not received"); and which receive wrote it. Notes hold codes and ids, never page text, formula text or values. This is where TRANSFORMED and PARTIALLY SUPPORTED live, and where the "not calculated here" state of a captured calculation (5.1) is recorded per property.
3. **On the source set: the receive ledger.** One record per receive (belonging to the source set of 5.2) holding: route; time; the **known source scope** (below); totals per state and cause; and one entry for every source element that has no Notaya item at all (NOT CAPTURED or DROPPED), with its source id or file path inside the hand-over, kind, cause and recoverability.

The ledger is an ordinary encrypted record with its own entry in the feature list, class optional (6.1): an older tolerant version can ignore it without harm.

### 7.3 Known source scope, and what counts and hashes may claim

Each receive stores exactly what was handed over: for a file route, the list of files with sizes and hashes; for an AI route, the source ids the AI declared it read, and whether it declared an inventory of the whole hub. Every count or hash comparison in a report is made against that scope and says so. Whether the scope was the whole source is UNKNOWN unless an inventory was provided, and even then it is the route's claim [REPORTED: pack 03: the file route never sees views or formula definitions]. Matching counts support "nothing known was dropped inside this scope". They do not support "the hub is complete", and they say nothing about exactness inside an element.

### 7.4 What the person sees (data needed, not screen design)

- In the page: "<kind> from Notion. Not available in Notaya yet. The original is kept." An older tolerant version shows the generic unknown-block placeholder with the same label. A pre-tolerant version cannot open the vault at all (section 6).
- On a database property: "stored value, not calculated here" for captured formula and rollup results.
- Per item and per source set: a list built from the notes and the ledger, grouped by state and cause, each line with its recoverability.

## 11. Dead ends to avoid for 2.0 to 2.5

Model only [PROPOSAL]; feature names are from the records [REPORTED: pack 04, 05] and were not studied in depth.

1. **A new kind without the tolerant reader** (dashboard, whiteboard, canvas). Each would be a forced upgrade with no way to open the vault read-only in the previous version.
2. **Canvas or whiteboard content stored as page-document nodes.** Free placement does not fit a block tree; it would break the additive rule or the node limits. Give such content its own kind that references pages and blocks by id.
3. **Code that assumes a block id is local to a page.** It closes the door on synced content and on blocks shown in two places. I3 with "move keeps, copy re-issues" keeps it open.
4. **References by title, path or position**, including new uses of the `#t:` heading form. They break on rename and on duplicate titles.
5. **A second identity scheme for rows or for imported items** beside item id plus origin (see Phase 0 item 7).
6. **The source id used as the Notaya id**, or a Notaya id derived from it. A second import, a merge of two sources or a change of app would then collide.
7. **A side table per feature** outside the encrypted record model. Each one is another thing that re-key, verification, backup and older versions must know about [VERIFIED at 95ca8b2: vault/mod.rs:451, 524: the 1.5.1 re-key covers two tables only].
8. **Stored structures hashed by re-serialising them.** Any added field breaks old hashes [VERIFIED: history.rs:152-153, 172-184].
9. **Closed lists with no "unknown" value** in stored data (kinds, property kinds, view kinds, import blocks).
10. **Binary floating point for values that must be exact** (money, measurements, ids that look like numbers).
11. **Header flag bits used as feature switches.** Unknown bits are treated as a corrupt file [VERIFIED: header.rs:249-251]; features belong in the feature list.
12. **Designs that only work because everything is in memory at unlock.** The reference index and the ledger are stored per item or per source set so that study 2 stays free to change loading.
13. **Calculated values stored as if they were entered values.** Once mixed with real data, a captured formula result can never be told apart again (5.1 keeps definition, captured definition and captured result separate).

## 12. Decisions for Ahmed

Each has a recommendation and what follows from it. None is taken by this study.

1. **Raise the storage format number in 1.6, or wait for 1.8?** Recommended: raise it in 1.6, together with the tolerant reader, after the one PC check of Phase 0 item 1. Consequence: Notaya 1.5.1 and older will refuse a vault that 1.6 has upgraded ("made by a newer version"), which changes the recorded expectation that 1.5.1 still opens it; in return an older version can no longer damage it silently. If you wait: one raise at 1.8, and until then the damage path stays open and must be stated in the release notes.
2. **Adopt option B ("versioned and tolerant", section 4) as the content model line?** Recommended: yes. Consequence: every later feature declares a class (required, read-only, optional) and from then on older tolerant versions open newer vaults read-only instead of failing.
3. **How the version is raised: full re-seal, or the lighter header-only variant?** Recommended: the full re-seal (the path that exists and is tested in the code), with its time measured on a large throwaway vault before release. The lighter variant needs a security review first. Consequence of the full path: an upgrade of a very large vault may take a long time and needs free disk of about twice the vault plus the backup [ESTIMATE, NOT RUN].
4. **Keep a small marker for items deleted for good?** It holds only an id, the kind and the time, so that a link can say "this was deleted" instead of "unknown". Recommended: yes. Consequence: a trace that something existed stays in the vault; with "no", purged and never-existed cannot be told apart.
5. **The backup wording and rule (G3).** The records disagree on whether you confirmed it (conflict C5). Recommended: confirm once more, using the draft in 6.5, with the rule "verified, named, never deleted automatically".
6. **History thinning.** Old versions are dropped automatically with no question asked. Recommended: keep it automatic but tell the person the rule once, and never thin the last version before an AI change or an upgrade. The alternative, asking each time, is safer and more tiresome.
7. **Old heading links that point by heading text.** Recommended: resolve one only when exactly one heading matches, report the rest, and offer at upgrade to rewrite the unambiguous ones to block ids, with a report. Consequence: some old links will show as "ambiguous" instead of jumping to the first match.
8. **Store source ids on the file import route now** (pulled forward from the 1.8 and 1.9 lists, as stored data only). Recommended: yes, before any real hub is imported to keep. Consequence if not: hubs imported before it can never be updated in place; they would have to be received again as new.
9. **When someone declines the upgrade:** recommended: the vault opens read-only in the new version until they accept. The alternative, full editing in the old format for ever, means keeping two formats alive.
10. **Stored originals of unsupported elements** (7.2) can hold private source text inside the vault, encrypted like everything else. Recommended: keep them, show them in the report, and let the person delete them per source set. Consequence of not keeping them: an unsupported element can only come back by receiving the source again.
11. **Weekly usage cap for the later study runs** (1b and after). None is set; this run recorded "weekly: UNKNOWN". No recommendation: it is your number to set or to leave unset.
12. **Order of area 3 and N2** (conflict C2) stays yours. This study adds only one constraint: N3's row identity is not finalised before Phase 0 items 3 and 6.
