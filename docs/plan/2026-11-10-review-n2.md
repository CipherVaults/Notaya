## Findings

### RVN2-M1 - A plain wrapper longer than 2,000 characters aborts the whole import

- **Where:** `src-tauri/src/commands/notion_db.rs:379`, reached from the header selection at `src-tauri/src/importers/plan.rs:539`; final database sanitization at `src-tauri/src/commands/notion_db.rs:542`, description limit at `src-tauri/src/database/types.rs:596`.
- **Reachable scenario:** select a ZIP containing `Home <id>.html` and `Home <id>.csv`, sharing an invented 32-hex id. HTML has the ordinary `article.page`, `header/h1.page-title`, `div.page-body` structure and one unformatted `<p>` of 2,001 `x` characters. CSV is `Name\nCard\n`. No links, children, icon or cover are needed. The planner accepts this as a deferred header, the database builder copies its text to `description` and marks the page removed, then `sanitize()` rejects the description. The error propagates out of the saving closure.
- **What a person sees:** the import fails with `The description is too long (at most 2000 characters).` Nothing from this import is committed; the existing vault is not deleted. The promised fallback page is not used. This weakens A53 item 5 for a legitimate longer introduction, hence **Medium**.
- **Proof:** used the existing count-only library probe on invented `description-2000.zip` and `description-2001.zip`. The 2,000-character control succeeded with one database/one row; the 2,001-character case exited 101 at the probe's `database stage failed` expectation (panic details deliberately suppressed by that harness). The exact error above is established by `Database::sanitize` / `check_len`, not an observed UI dialog. Logs are under the external review test root.
- **Smallest fix:** consume a header only if it fits the existing database description limit; otherwise keep the rendered source page. Do not truncate the text or increase the limit.
- **Regression:** extend `n2_plain_wrapper_text_is_saved_in_the_database_description_without_a_duplicate_page` with 2,000/2,001-character cases through `import_from`, persist/reopen, and assert that the longer case imports its database plus the complete fallback page. The present short-header test cannot catch this late validation failure; the failed-table test exercises CSV parse failure instead.

### RVN2-M2 - An empty-body HTML source home is discarded before its children are paired

- **Where:** `src-tauri/src/importers/plan.rs:530` (unconditional empty-body return), before the source-home protection at line 539; `files_of` passes the already-known `has_folder` at line 357.
- **Reachable scenario:** `Home <id>.html` is a title-only structured source document, `Home <id>.csv` contains `Name\nCard\n`, and `Home/Child.md` contains `# Child\n\nChild body\n`. The id-less sibling folder proves this is a source home with children. The shared CSV id puts it in `database_html`; its empty converted body causes `document` to return `None`, so `files_of` never pairs that folder. Generated/source cleanup does not get a chance to protect the home.
- **What a person sees:** the genuine Home page is absent, its Child becomes a root in a separate Home section, and the database is in the loose section. This breaks A53 items 1 and 3, hence **Medium**. A genuinely empty view without child structure should still create nothing.
- **Proof:** invented `empty-source-home.zip` through the existing count probe succeeded but produced **1 page, 2 sections, 0 shallow source documents planned/surviving**. The identical `nonempty-source-home.zip`, adding only `<p>Home instructions</p>`, produced **2 pages, 1 section, 1 shallow source document planned/surviving**. The inputs each contain two source documents. Static tracing identifies the early return above; no UI was run.
- **Smallest fix:** exempt structurally identified source homes from the empty-wrapper drop before deciding that the wrapper is redundant. Preserve the source page and its parent relationship; do not create empty pages for ordinary view-only wrappers.
- **Regression:** extend `n2_wrapper_navigation_formatting_children_and_multiline_text_stay_on_pages` with an empty body and an id-less child folder, then assert the Home id survives, Child.parent is that id, and there is one section. `n1_title_only_source_home_survives_row_cleanup` is strong for Markdown ancestor cleanup but does not exercise HTML/CSV wrapper classification; the current HTML child test always supplies nonempty prose.

### RVN2-L1 - Colliding clean names cause a quadratic scan in the new pairing rule

- **Where:** `src-tauri/src/importers/plan.rs:359`, inside the per-file loop at line 345.
- **Reachable scenario/proof:** place N sibling documents `Home <distinct-id>.md` beside N sibling folders `Home <other-distinct-id>/Table.csv`. Every clean name is `home`, but no folder is id-less and no exact id matches. `dirs.iter().any(idless)` therefore visits all N folders for every one of the N documents, repeatedly allocating in `strip_notion_id`: N-squared work despite the maps. CSV-only folders now enter this tree, so this does not require exceeding the document cap.
- **Observed effect:** invented complete count-probe runs for N=500/1,000/2,000 reported **540/1,379/4,607 ms**, respectively. These include all probe stages and are not isolated pairing timings; the code establishes the complexity. The largest source has 4,000 entries and 2,000 documents. No hang, crash, exhaustion or security-boundary bypass was demonstrated; **Low**, a bounded performance/hardening defect under the explicit large-tree review criterion.
- **Smallest fix:** calculate whether a clean-name group contains an id-less folder once when building `clean_dirs`, then reuse it. Keep the current ambiguity refusal.
- **Regression:** add a same-clean-name collision scaling case to `many_files_with_folders_named_like_pages_are_matched_quickly`, with distinct document/folder ids and CSV-only folders. Guard the matching work with an operation-count or scaling assertion. The existing test uses different clean groups (`Page i` versus `PAGE i extra`), so it never exercises this repeated scan.
