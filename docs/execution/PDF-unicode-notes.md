# PDF export: Arabic, Hebrew, Chinese, Japanese, Korean (working notes)

Baseline: `origin/main` `ee8c32e` (V1.4.0). Owner's words (via the coordinator): "PDF export prints Arabic, Hebrew and Chinese/Japanese/Korean letters as '?'. do it as well in the version". Result state: **produced and verified in the cloud (Wine); not integrated, not accepted.** Written on 2026-11-03 (system clock, UTC). These are working notes of the PDF helper, not an Execution Summary; the lead decides on the formal record.

## What changed

New files in `src-tauri/src/export/` (no new crate; everything hand-written like the ZIP, DEFLATE and PDF writers):

| File | What it does |
|---|---|
| `ttf.rs` | TrueType reader (single fonts and `.ttc`, cmap formats 4 and 12, advances, glyph bounds, PostScript name) and subsetter (keeps glyph numbers, cuts the tables after the last used glyph, follows composite glyphs, drops hinting instructions, rewrites `head`/`hhea`/`hmtx`/`loca`/`glyf`/`maxp` with correct checksums). Refuses CFF fonts and fonts whose OS/2 `fsType` has the restricted-licence bit (0x0002), the no-subsetting bit (0x0100) or the bitmap-only bit (0x0200). All reads are bounds-checked. |
| `arabic.rs` | Arabic shaping with Unicode Presentation Forms (FB50 and FE70 blocks): joining types, isolated/final/initial/medial forms, lam-alef ligatures (4 forms), tashkeel kept and transparent, tatweel, ZWJ/ZWNJ, Persian/Urdu letters (peh, tcheh, keheh, gaf, farsi yeh, jeh, ...). |
| `bidi.rs` | Compact UAX #9: paragraph level from the first strong character (P2/P3), W1-W7, N0 (paired brackets), N1/N2, I1/I2, L1, L2 (`visual_order`), mirroring (L4). Explicit embeddings/overrides/isolates are NOT implemented (those characters are ignored; LRM/RLM count as strong). |
| `pdf_unicode.rs` | Font pool: bundled Arabic and Hebrew subsets, CJK fonts read from `%WINDIR%\Fonts` (via the `WINDIR`/`SystemRoot` variable, fixed file names only, 96 MB cap, nothing from the user), glyph lookup, and the five PDF objects per embedded font (Type0 Identity-H, CIDFontType2 with `/W`, FontDescriptor, FontFile2, ToUnicode). |

Changed: `pdf.rs` (layout and writer), `mod.rs` (modules; `ExportSummary.chars_no_font`), `THIRD-PARTY-NOTICES.md`, `packaging/Licenses/` (two OFL texts and the README), `tools/make-pdf-fonts.py`, `src-tauri/fonts/` (two subset fonts).

How the pipeline works in `pdf.rs`:

1. A hard line (paragraph or line after a break) with no Arabic/Hebrew/CJK/direction-mark character goes through the old code unchanged (`simple_line`).
2. Otherwise (`complex_line`): bidi levels for the whole paragraph, Arabic shaping, each character gets its font (Helvetica/Courier for Western text, the Arabic font, the Hebrew font, a system CJK font), neighbours with the same style, level and font become pieces, CJK characters are their own pieces with break opportunities between them (simple kinsoku: no line start before closing punctuation and small kana, no line end after opening brackets). The font for a Han character follows the script of its line (kana: Japanese fonts first; Hangul: Korean first).
3. Wrapping is done on the logical pieces; then each line is reordered visually (`visual_order`) when it has an odd level. RTL paragraphs (first strong character is Arabic or Hebrew) are right-aligned (Left and Justify become Right; Center stays). Brackets are mirrored. Code blocks keep a left-to-right paragraph level.
4. List items that start with RTL text have the marker on the right (bullet, `.N` for numbers, checkbox) and the indent on the right.
5. Marks (Arabic tashkeel, Hebrew points) are centred over the letter before them from the glyph outline bounds (shin dot at the right, sin dot at the left, holam left, second mark on a letter raised/lowered 0.3 em). Bold and italic Arabic/Hebrew are synthetic (stroke width, 0.2 shear) because only one weight is bundled.
6. Content stream: pieces are written in reading order, glyphs inside a piece right-to-left in drawing order, each right-to-left piece wrapped in `/Span << /ActualText <FEFF...> >> BDC ... EMC` with its text as written (so Acrobat-style copy and search get the original letters, not presentation forms; the ToUnicode map also maps presentation forms back to the base letters and lam-alef to two letters).
7. Western-only documents: the output is **byte-for-byte identical to V1.4.0** (checked with a temporary test that rendered the V1.4.0 `pdf.rs` side by side on the every-node sample and a 150-paragraph document with accents, euro, arrows, emoji, Cyrillic, links, lists and code; the test and the old copy were then removed).

Report fields: `Output.chars_replaced` still counts every character shown as "?" (or left out); new `Output.chars_no_font` / `ExportSummary.chars_no_font` (serialised as `charsNoFont`) counts Chinese, Japanese and Korean characters for which the PC has no usable font at all. **Not done (the UI is outside my write area):** `src/features/notes/ExportDialog.tsx` line 140 still says "Some characters are not available in PDF and were replaced. Export to Word to keep them." and `src/lib/types.ts` line 195 needs `charsNoFont: number;`. Suggested text: when `charsNoFont > 0`, "No font was found for Chinese, Japanese or Korean on this PC, so those characters were replaced with ?. Export to Word to keep them." Also the sentence in `docs/security-design.md` P25 "Limits" ("Arabic, Hebrew, CJK and other scripts become `?`") is out of date once this is merged (Arabic, Hebrew and CJK now print; Greek, Cyrillic, other scripts and emoji still do not), and the new file read (system font files, read-only, fixed names, size-capped) belongs in P25.

## Font decision

* **Arabic: Noto Sans Arabic Regular** (SIL OFL 1.1, no Reserved Font Name, copyright 2022 The Noto Project Authors), static TTF from the npm package `@expo-google-fonts/noto-sans-arabic` 0.4.3. Its cmap has all of Arabic Presentation Forms-B (U+FE70 to U+FEFC) and the Persian/Urdu forms in FB50-FBFF, so no GSUB is needed. Checked with fontTools; a unit test checks every form the shaper can produce is in the bundled font. (Amiri and Noto Naskh also have them but are 421 KB and 200 KB; DejaVu is not OFL.)
* **Hebrew: Noto Sans Hebrew Regular** (same licence, 0.4.1 package).
* Both are reduced with fontTools 4.68.0 (`tools/make-pdf-fonts.py`): only the Arabic block, FB50-FBFF, FE70-FEFF, ZWJ/ZWNJ, NBSP and space (Arabic), the Hebrew block and FB1D-FB4F (Hebrew); GSUB/GPOS/hinting dropped; outlines unchanged. Sizes: 194,176 -> **37,128** bytes and 48,036 -> **9,636** bytes.
* **CJK: system fonts at export time**, file names tried in order (Han: `msyh.ttc`, `simsun.ttc`, `Deng.ttf`, `msjh.ttc`, `mingliu.ttc`, `YuGothR.ttc`, `meiryo.ttc`, `msgothic.ttc`, `malgun.ttf`; kana: `YuGothR.ttc`, `meiryo.ttc`, `msgothic.ttc`, `YuGothM.ttc`, then Chinese ones; Hangul: `malgun.ttf`, `gulim.ttc`, `batang.ttc`, then Chinese ones). First font in the collection only. CFF-outline or licence-restricted files are skipped. No CJK font is bundled (they are 5 to 20 MB). If none is found, the characters become "?" and are counted in `chars_no_font`.
* **Installer cost:** the two fonts add 46,764 bytes to the exe (compiled in with `include_bytes!`), plus about 40 to 60 KB of new code (not measured, release build not made), plus 8,764 bytes of licence texts in `Licenses\`. Total roughly 0.1 MB before the installer's compression. Each PDF carries only the used glyphs: the sample PDF with all five scripts is 59 KB.

By hand on the sample PDFs in `/mnt/project-files/notaya-build/v150-pdf/` (`unicode-samples.pdf`, `unicode-samples-no-cjk-font.pdf`, page PNGs, a zoom of Hebrew points): `pdfinfo`, `pdffonts` (all fonts embedded, subset, with Unicode map), `pdftoppm` (looked at: joined Arabic, right-to-left, right-aligned paragraphs and headings, mixed Arabic/English/number lines, brackets, tashkeel, Hebrew with points, Chinese, Japanese, Korean left to right wrapping at any character, Arabic bullet and numbered lists with the marker at the right, table cells, code block; the no-CJK-font file shows `?` and reports 183 characters). Text extraction: **pypdf** returns the Arabic and Hebrew words in reading order; **pdf.js** (pdfjs-dist 4.10.38 in Node) returns the words in reading order (it drops the spaces between right-to-left words and reverses the two letters of a lam-alef ligature, both known pdf.js habits with any generator); **pdftotext (poppler)** returns right-to-left text in visual order with each word reversed, which is poppler's normal behaviour for right-to-left PDFs and does not use the ActualText.

## Not run / limits

* **Not run:** the real Windows system fonts (Microsoft YaHei, Yu Gothic, Meiryo, Malgun Gothic, SimSun, MingLiU, ...), so the file names, whether Yu Gothic is TrueType or CFF, and the `fsType` of these fonts are unconfirmed on a real PC. In the container the CJK path was tested with a synthetic test font (always) and with WenQuanYi Zen Hei (TrueType, `fsType` 8) and IPAPGothic copied under the names `msyh.ttc`, `malgun.ttf` and `YuGothR.ttc` into a test folder (sample files only; not bundled). Not run: Adobe Reader, Microsoft Edge/Chrome (pdfium) and other viewers; the real exe; MSVC `cargo clippy`; the UI (`tsc`, `npm run build`: no file in `src/` changed); the Windows installer or portable ZIP build.
* Greek, Cyrillic, Thai, Devanagari and other scripts, and emoji, still print "?" (emoji left out), as before.
* Arabic: one weight (regular; bold and italic are synthetic), no optional ligatures, kashida or stylistic features, marks placed by centring (no GPOS), no contextual alternates. Hebrew points are centred with small fixes; unusual stacking can overlap.
* Bidi: explicit embeddings, overrides and isolates are ignored. An explicit left alignment on an RTL paragraph prints right-aligned (the model cannot tell it from the default). The other helper's direction field (if added to the model) is not used; direction is found from the first strong character.
* PDF extraction by poppler is in visual order (see above); copy and search in viewers that read ActualText or do their own bidi are fine, but this is not proven for Acrobat, Edge or Firefox.
* A CJK glyph shared by two characters in a font is mapped to the first one in ToUnicode.
* CJK vertical text, ruby, kinsoku hanging punctuation, Japanese justification: not done.
* Loading a real CJK font reads a 10 to 20 MB file into memory for the export and drops it afterwards.
