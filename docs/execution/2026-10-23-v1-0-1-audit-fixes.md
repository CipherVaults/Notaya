## Addendum 2026-10-24 01:3x UTC: second independent review and its fixes

A second read-only review agent (model output, effort max) read the whole diff at `595bf59` and ran six probes in a scratch copy of the harness. No High findings. Fixed in the next commit (all in the cloud harness, 109 tests pass; PC results below once recorded):

1. **Hourly backups collapsed the history (Medium, confirmed by a probe):** ten day-spaced backups plus ten hourly ones left none of the old ones. Now the hourly backup is `vault-hourly-<ms>.clf` in its own rotation (newest 3), uses its own `Session::hourly_due` flag, and no longer clears the flag that makes the lock/quit backup, so every session end still adds an ordinary backup.
2. **The failure notice reassured when it should not (Medium, confirmed):** SQLite corrupt, not-a-database, I/O errors and every other file error ended with "Your notes are still saved". Now it reassures only for a full drive, access denied, read-only, file in use, already exists (the place the copy goes to); every other cause says the vault file or the drive may be at fault and to keep other copies.
3. **The hourly backup could freeze the window on slow media (Medium, blocking confirmed, duration plausible):** it now starts only after 30 seconds without keyboard or mouse input (or when 90 minutes overdue, so a PC that is never idle is still backed up).
4. **F-13 missed an existing read-only data folder and a window that fails to open (Low):** `ensure_dirs` now creates and removes a probe file, and a failing `build_main` shows a message box too.
5. **Turning security on also deletes `vault-predelete-*` (Low, by design but not said):** the dialog and README now say that safety copies (and hourly copies) are deleted with the other unprotected backups.
6. **No retry on the flush, and a failed hourly backup waited an hour (Low, plausible):** the flush retries like the rename (5 times, 250 ms apart); a failed hourly backup is retried after 5 minutes and shown once.
7. **Wording (Low):** the delete confirm now says that Restore replaces the whole vault with the safety copy (the current one is kept as `restore-undo`); README, security-design (re-key, hourly only with security off, 1 s per 200 MB is an SSD figure), acceptance (V1e test name, V4 contradicted by the live check) and the README version banner were corrected.

Not changed, recorded: a backup, password change or delete fails if any record or attachment cannot be decrypted (consistent with restore); an open vault does not notice drive removal (pre-existing, F-03); synchronous commands run on the main thread, so any long hold of the session lock freezes the window (pre-existing).

A test hook was added with these fixes: the environment variable `CIPHERLEAF_OPEN_BACKUP_SECS` (a whole number of seconds, read like `CIPHERLEAF_HOME` in release builds too) shortens the hourly backup interval and its retry interval to that number and drops the 30-second pause, so the real-exe scripts can watch the hourly backup without waiting an hour. Without it nothing changes.
