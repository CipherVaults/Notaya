# ▶️ Lifecycle prompts — v1.0 candidate

These prompts are new synthesis from observed project practices. They are not recovered original templates, implementation permission, or adopted v1.0 policy. Replace placeholders and carry forward the user's actual authorization. Use the project's established record formats.

## Start a project or bounded task

```text
Help me establish [task/project] within [authorized scope]. Read the applicable instructions and inspect the smallest relevant source set first. Report what you actually inspected and what remains unknown. Explain the desired outcome, constraints, existing work, decision owner and proposed stopping point. Identify which questions need durable records and who owns each; use a compact record where separate files would add no value. Propose a concrete approach and meaningful verification. Preserve sources and private information. Do not treat a draft Plan or this template as authority for actions outside the scope I gave you.
```

## Recover context without replaying completed work

```text
Resume [task/project] from [checkpoint]. Read current instructions, the latest applicable authority, Current State/Continuation and the relevant session or execution record. Reconcile those records against the available current artifacts and evidence. Distinguish accepted work, complete-but-unreconciled work, implemented-but-unverified work, partial work and unknown state. Identify stale or conflicting claims, known failed approaches and what must not be repeated or overwritten. State the exact first permitted unfinished action. Continue work already authorized; if a missing decision blocks dependent work, preserve the checkpoint and identify that specific decision while continuing independent approved work where useful.
```

## Review or amend a proposed Plan

```text
Review [Plan] against [desired outcome / existing Goal] and [sources]. Assess coverage, assumptions, alternatives, dependencies, capability proofs, verification, recovery and the proposed stopping point. Explain material gaps and propose concrete amendments. Preserve rejected options and their reasons. Separate changes within existing authority from changes requiring an owner decision. Make the result reviewable; do not present the Plan itself as execution authorization. Record whether it is proposed, reviewed, amended or approved, with the supporting decision source.
```

## Execute an approved bounded Goal

```text
Execute [Goal] under [approval/amendment source] using [Plan]. First reconcile current authority, surviving work and the exact checkpoint. Work through the next bounded step, adapting implementation details within the approved scope as evidence warrants. Preserve useful failures and interrupted work. Stop dependent work at an actual review gate, material scope change, explicit pause or essential capability block; do not invent extra approval gates for ordinary authorized work. Verify the named criteria, distinguish technical result from owner acceptance, and record concrete work and evidence in the established Execution Summary. Keep Current/Continuation and other changed owners coherent without duplicating the same narrative everywhere.
```

## Verify a result and prepare acceptance

```text
Assess [candidate] against [criteria]. Identify the exact source/artifact/configuration each check applies to. Record what was directly checked, what is only a prior recorded result, and what remains untested. Separate outcome, applicability and acceptance decision, including not-run, inconclusive and unavailable states. Retain failed evidence and explain which observations remain usable after correction. Do not promote a component test into integrated-product proof, a file copy into working recovery, or a technical pass into user acceptance. Do not waive an unmet mandatory criterion through “accepted with limits”; preserve the criterion or identify the explicit authorized exception/amendment. Present the bounded result and the actual decision still needed, if any. Avoid repeating expensive work when existing applicable evidence is sufficient.
```

## Update documentation after meaningful work

```text
Reconcile documentation for [event/milestone] using [evidence]. Before editing, identify each record's primary question, exclusions and update trigger. List which owners' answers actually changed. Update those records proportionately, preserving sound content and historical truth; use links to the detailed owner instead of copying the same checkpoint into every file. Keep the full established Session Summary format for substantive continuity, and a separate factual Execution Summary when appropriate. Do not fabricate model identity, time, approvals or successful publication. Verify the saved destination, links, chronology, preserved history and consistency of current authority/acceptance. Record no-change rationale for likely affected owners that were reviewed but remain correct.
```

## Record a session faithfully

```text
Write the session record for [period/topic] using the project's established full template and exact heading hierarchy. Preserve the starting intention separately from discoveries and later scope changes. Include chronological actions, user-visible reasons, considered/rejected options, decisions and their status, friction and user context that affected the work, adjustments, mistakes/risks, Before/After/Current standing, concrete next steps, genuine open questions, outcome and scoped confidence. Add known roles/model/effort/provenance without guessing; distinguish the original work from a later reconstruction/editor. Retain every required core section with concise honest content when little happened. Use optional sections only where useful. Preserve older entries and the defined archive order. Do not expose hidden reasoning or private source material in a shareable version.
```

## Interrupt or hand off

```text
Checkpoint [task/project] at [stopping condition]. Preserve current authority, exact completed/partial/unverified work, artifact identities, relevant live process or tool state, evidence limits, failed approaches and useful uncommitted or unsaved work. Record what must not be repeated, the first permitted continuation, and the decision or evidence needed if waiting. Reconcile affected Current/Continuation/Goal/Plan/report/index records within the authorized scope. Identify the intended recipient/task and its access limits; do not assume another conversation sees these files. Mark the handoff accurately as prepared, delivered, acknowledged, executed or accepted based on evidence. Do not infer scheduler state or future resumption authority.
```

## Close a bounded Goal

```text
Close [Goal] only to the extent supported by its agreed criteria and acceptance decisions. Reconcile final evidence, remaining limitations, owner review, preserved artifacts and affected record owners. Distinguish optional later improvements from blocking unfinished scope. State any publication/read-back or recovery checks not completed. Preserve the last exact checkpoint and links to execution/session history. Confirm any authorized background-work closure through evidence; if a control action cannot be verified, say so. Do not create new backlog or resume unrelated work to avoid ending an accepted bounded Goal.
```
