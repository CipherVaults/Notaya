**Status:** sanitized research extraction for review. The established section responsibilities, order, emoji markers, detailed guidance, optional sections and original H3 quick skeleton are retained. Personal names and private-domain examples are replaced with neutral research-library examples. This is an adaptation, not a byte-verbatim original or an adopted replacement policy.

**How to use:** preserve the project’s accepted heading hierarchy. The general source’s explanatory template uses H2 sections and its quick skeleton uses H3; the separately supplied multi-project wrapper uses H1 sessions, H2 projects, H3 overview/handoff, H4 core sections and H5 deeper chronology. Choose the established format explicitly. Do not silently merge core sections to shorten the document. Write only supported facts, decisions, user-visible rationale and genuine uncertainty.

**Authority boundary:** the historical instruction that Current Position should support resumption “alone” describes context recovery. Before executing, reconcile the latest applicable authorization, current artifacts and evidence. A historical session or this template does not grant permission to resume paused work.

## Purpose of This Template

This template defines how session summaries should be written for the project owner’s long-term projects.

A session summary is not a shallow recap.

It is a **project-memory document**.

Its job is to help the future project owner, reasoning partner, execution agent, or another AI thread re-enter the project without needing to reread the entire conversation.

A good session summary should preserve:

- what happened

- why it mattered

- what decisions were made

- what changed during the session

- what remains unresolved

- where the project currently stands

- what should happen next

The summary should be detailed enough to restore context, but not bloated with repeated explanations that belong in Architecture, Roadmap, README, or other project documents.

---

## 🧱 Core Writing Rules

### 1. Write for Re-entry

The reader may return days, weeks, or months later.

Write so they can understand:

- where the project was before the session

- what changed during the session

- where the project stopped

- how to continue

---

### 2. Preserve the Thinking Path

Do not only write final decisions.

Also preserve the reasoning journey:

- what was considered

- what was rejected

- what changed

- why the final direction became clearer

---

### 3. Do Not Duplicate Full Project Documents

The session summary should not become another Architecture document, Roadmap, Taxonomy, or README.

It may reference those documents, but it should focus on the session’s evolution.

---

### 4. Use Clear Section Hierarchy

Use large section titles with emojis.

Avoid writing the whole summary as one flat wall of text.

Each section should have a specific job.

---

### 5. Be Detailed, Not Inflated

Do not add unnecessary words just to make the summary look deep.

Prefer useful specificity over generic explanation.

Bad:

“The project progressed meaningfully in several areas.”

Good:

“Architecture v0.1 was drafted, Roadmap v0.1 was drafted, and the next step shifted from Source Taxonomy to Human Entry Specification after the dense normalization format was rejected.”

---

### 6. Capture Friction Honestly

Session summaries should include confusion, mistakes, rejected ideas, frustration, and changes in direction.

These are often more valuable than the clean final output.

---

### 7. End With a Clear Re-entry Point

The next session should know exactly where to begin.

---

## 📘 Session: [Date] — [Project Name] [Main Session Theme]

Example title format:

📘 Session: [Date range] — Research Library Foundation, Architecture, Roadmap, Research Log Review, and Human-Friendly Capture Methodology Discovery

Use a long descriptive title when the session covered many important layers.

The title should answer:

- when the session happened

- which project it belongs to

- what the session mainly achieved

## 🕒 Time

Use this section to quickly identify the session.

Template:

- Start: [Date / time if known]

- Continuation: [Additional dates if split across days]

- Total Working Hours: [Approximate, optional]

- Session Type: [Planning / re-entry / implementation / review / Codex integration / documentation / debugging / etc.]

- Project Stage: [Foundation Layer / Phase 4 / Capture Layer / Analysis Layer / etc.]

- Main Focus: [One sentence explaining the session’s central purpose]

Rules:

- Do not over-explain here.

- This is metadata.

- Keep it short and readable.

---

## 🎯 Session Goal

This section explains what the session was trying to accomplish.

It should include:

- the starting intention

- why the session was needed

- what problem the session tried to solve

- what the desired stopping point was

Good structure:

- Begin with a short paragraph.

- Then list the concrete goals.

Template:

The goal of this session was to [main purpose].

This session was needed because [context / problem].

The session aimed to:

- [Goal 1]

- [Goal 2]

- [Goal 3]

- [Goal 4]

Rules:

- Do not include everything that happened.

- Only explain what the session was trying to do.

- Actions belong in the next section.

---

## 🛠️ Actions Taken

This is the chronological “what happened” section.

It should list the actual work performed during the session.

Use bullets.

Include concrete actions, not vague statements.

Good examples:

- Re-entered the project after a pause.

- Reviewed the previous roadmap.

- Uploaded and reviewed the research log.

- Drafted Project Architecture v0.1.

- Rejected the first dense normalization format.

- Reframed the next step as Human Entry Specification v0.1.

Rules:

- This section can be long if the session was long.

- It should preserve sequence.

- It should not deeply explain every action; deeper meaning belongs in Key Insights or Decisions.

- Use nested bullets only when useful.

---

## 🧠 Key Insights

This is one of the most important sections.

It explains what the session revealed.

A key insight is not merely something that happened.

It is something the project now understands better.

Template:

- [Insight]

- Why it mattered:

   - [Explanation]

- What it changed:

   - [Consequence]

Examples:

- The project is not a simple bookmark list; it is a research memory system.

- Source-level detail is not optional because it preserves source history.

- Human capture and machine structure are different layers.

- Codex should interpret the project owner’s writing, not force the project owner to write like a database.

Rules:

- Do not list every small observation.

- Focus on discoveries that affect future work.

- This section should preserve the “meaning” of the session.

---

## 📌 Decisions Made

This section records concrete decisions.

A decision is something the project should treat as settled unless reopened later.

Use direct bullets.

Good examples:

- The project will use Hybrid Mode.

- Knowledge Entry is the atomic object.

- Notion is the likely Capture Layer.

- Excel is the likely Analysis Layer.

- Dense human-facing normalization is rejected.

- Current State should wait until the foundation is more stable.

Rules:

- Decisions should be clear.

- Avoid turning insights into decisions unless something was actually chosen.

- If a decision is provisional, say so.

Useful labels:

- Confirmed:

- Provisional:

- Deferred:

- Rejected:

---

## ⚠️ Difficulties / Friction

This section captures what was hard, confusing, or unstable.

It should include:

- disagreements

- uncertainty

- user frustration

- technical limitations

- unclear next steps

- competing options

- design tension

Examples:

- The first normalization format was too dense for daily use.

- The project had to balance human readability against machine structure.

- It was unclear whether Source Taxonomy or Session Summary should come next.

- Current State felt premature.

Rules:

- Do not hide friction.

- Friction is part of project memory.

- Write it calmly and analytically, not defensively.

---

## 🔧 Adjustments Made

This section explains how the project changed direction during the session.

It should usually be written as “shifted from → to.”

Template:

- Shifted from:

   [old framing]

   to:

   [new framing]

Examples:

- Shifted from:

   bookmark list

   to:

   research memory system

- Shifted from:

   single source of truth

   to:

   capture once, analyze many

- Shifted from:

   dense structured Markdown

   to:

   human-friendly capture with machine-rich interpretation

Rules:

- This section is especially important when the session involved design evolution.

- It helps future readers understand why the project no longer follows the initial idea.

---

## ❌ Mistakes / Risks Noted

This section records mistakes, risks, or near-mistakes.

It is not for blaming.

It is for preventing repeat confusion.

Use this section for:

- wrong assumptions

- dangerous directions

- ideas that were caught before implementation

- risks that need future attention

Examples:

- The dense normalization proposal would have made the system harder for the project owner to maintain.

- There is a risk of letting Codex invent categories on the fly.

- There is a risk of rewriting the full log before the entry format is approved.

- There is a risk of over-documenting before implementation.

Rules:

- If no major mistake occurred, say so.

- If a mistake was caught early, say that.

- Mention whether a Failure Intelligence entry is needed.

Example closing line:

No Failure Intelligence entry is required yet because the issue was caught during design rather than after implementation.

---

## 📍 Current Position

This section is the re-entry anchor.

It should clearly explain where the project stands now.

Use:

Before this session:

- [State before]

After this session:

- [State after]

Current standing:

“[One sentence that captures exactly where the project stopped.]”

Example:

Before this session:

- The research log existed, but the project was not architecturally defined.

- There was no roadmap.

- Codex’s future role was unclear.

After this session:

- Architecture v0.1 exists.

- Roadmap v0.1 exists.

- Knowledge Entry is the core concept.

- Human-Friendly Capture, Machine-Rich Interpretation is the guiding principle.

- The next step is Human Entry Specification v0.1.

Current standing:

“The project understands what it is; now it needs to define the simplest sustainable way the project owner should write research observations.”

Rules:

- This section should be extremely practical.

- A future thread should be able to resume from this section alone.

---

## 🔜 Next Steps

This section lists what should happen next.

It should be concrete and sequenced.

Template:

- [Next step 1]

- [Next step 2]

- [Next step 3]

- [Next step 4]

For complex projects, include the recommended next-session flow.

Example:

- Begin the next session by reviewing this Session Summary.

- Design Human Entry Specification v0.1.

- Test the format on [sample period 1].

- Test the format on [sample period 2].

- Adjust and approve the format.

- Begin Source Taxonomy v0.1.

- Rewrite the full project log after the format is approved.

Rules:

- Do not make the next steps too broad.

- Do not list distant future work unless it affects the immediate path.

- The first next step should be obvious.

---

## ❓ Open Questions

This section preserves unresolved issues.

Open questions should be real, not filler.

Examples:

- Should Human Entry Specification and Source Taxonomy be separate documents?

- Should Markdown remain the capture source, or should Notion become the capture source later?

- Which fields are mandatory in every research observation?

- Should tags be written manually or inferred by Codex?

- When should Codex enter the project?

Rules:

- Use questions, not statements.

- Keep them relevant to the next phase.

- Avoid adding huge speculative future questions unless they are already active.

---

## 🧾 Session Outcome

This section summarizes what the session accomplished at the highest level.

It should be written narratively.

It should answer:

- What changed because this session happened?

- What is now clearer?

- What did the session prevent?

- What is the project now ready for?

Example structure:

This session completed [main accomplishment].

It did not [things intentionally not done].

Its main accomplishment was [real value].

By the end of the session:

- [Outcome 1]

- [Outcome 2]

- [Outcome 3]

The project is no longer asking:

“[old question]”

It is now asking:

“[new question]”

Rules:

- This section should feel like closure.

- It should not repeat every action.

- It should explain the meaning of the session.

---

## 🔍 Confidence Level

Use a clear confidence label.

Options:

- Low

- Medium

- Medium-High

- High

- Very High

Then explain why.

Template:

Confidence Level:

[High / Medium-High / etc.]

Reason:

- [Reason 1]

- [Reason 2]

- [Reason 3]

Not higher because:

- [Unresolved issue 1]

- [Unresolved issue 2]

- [Unresolved issue 3]

Rules:

- Be honest.

- Do not say “Very High” just because progress was good.

- Confidence should reflect how stable the project direction is.

---

## 💬 Personal Note

This section is optional but often valuable for long-lived projects.

It captures the emotional, philosophical, or human meaning of the session.

It should not be sentimental unless the session genuinely had emotional weight.

It should answer:

- Why did this session matter personally?

- What should the future project owner remember?

- What deeper theme appeared?

- What human reality did the system need to respect?

Example:

This session mattered because it protected the project from becoming technically impressive but humanly unusable.

The system should not force the project owner to write like Excel.

It should let the project owner write naturally and let the tools carry the structural burden.

Rules:

- Keep it meaningful.

- Do not overdo it.

- This section should feel like the human closing note of the session.

---

## 🧩 Optional Sections

Use these only when needed.

---

### 📚 Files / Documents Created or Updated

Use when the session created real project files.

Include:

- file name

- status

- purpose

---

### 🤖 Codex Work Performed

Use when Codex did meaningful work.

Include:

- what Codex was asked to do

- what it created or changed

- what was verified

- what remains unresolved

- whether an Execution Summary exists

---

### 🧪 Validation / Testing

Use when something was tested.

Include:

- what was tested

- result

- what failed

- what remains uncertain

---

### 🗂️ Documentation Updates Needed

Use when the session implies future documentation changes.

Examples:

- update Roadmap

- update Current State

- create Session Summary

- update README

- update CHANGELOG

---

### 🚫 Deferred Work

Use when many tempting tasks were intentionally postponed.

Examples:

- Notion implementation deferred

- Excel dashboard deferred

- Codex task brief deferred

- Power BI deferred

## 🧠 One-Sentence Rule

A session summary should not be a transcript, and it should not be a replacement for project documents.

It should be the clearest possible bridge from:

“What happened last time?”

to:

“Where do we continue now?”
