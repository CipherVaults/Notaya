# 📘 Session Format Profiles

## What this guide owns

This guide distinguishes the candidate's two copyable Session Summary profiles, their source lineage, and their adoption and navigation rules. It complements the full [writing method](write-session-summaries.md); it does not replace the detailed methodology with a list of headings.

The candidate retains both a portable single-project form and a source-established multi-project form. Neither is declared the latest universal structure, and inclusion here is not project adoption or a stable-release claim. A project's already accepted form remains in force until a deliberate change is approved.

A short execution report can be the right record for a bounded operational task. It is a different artifact. Do not call a four-heading recap a full Session Summary after removing the adopted session's section responsibilities.

## Exact multi-project hierarchy

The hierarchy is intentional, including the session-level H3 headings before the first H2 project:

- H1: 📘 Session title, identifying date or date range and the main work
- H3: 🕒 Time for session-level orientation
- H3: Projects covered, with an explicit project index
- H2: 1. [Project] — [Descriptive topic], followed by subsequent numbered project blocks
  - H4: 🤖 Models, Effort, Roles and Provenance
  - H4: the thirteen core sections in the order below
  - H5: descriptive chronological blocks or other meaningful deeper subsections
  - H4: applicable optional sections, after the core
- H3: Session handoff, preserving each project's exact endpoint

The H3 session metadata and H4 project Time sections have different jobs: one orients the coordination session; the other records the particular project's work and cutoff. Neither should be an invented total of the other's elapsed time.

Do not flatten projects into H3, move the project core to H2, or relabel H5 chronology as another peer project. The established wrapper is a named profile rather than a universally imposed outline. A renderer's automatic outline may display the intentional H3/H2 transitions unusually; verify the actual destination instead of quietly changing the contract.

### Per-project sequence

The provenance block precedes these exact H4 identities:

1. 🕒 Time
2. 🎯 Session Goal
3. 🛠️ Actions Taken
4. 🧠 Key Insights
5. 📌 Decisions Made
6. ⚠️ Difficulties / Friction
7. 🔧 Adjustments Made
8. ❌ Mistakes / Risks Noted
9. 📍 Current Position
10. 🔜 Next Steps
11. ❓ Open Questions
12. 🧾 Session Outcome
13. 🔍 Confidence Level

Keep all thirteen in each substantive project block. Personal Note is optional. The provenance block is a wrapper addition before the core, not a fourteenth core section inherited from the original generic skeleton. Keep Current Position's **Before this session**, **After this session**, and **Current standing** distinctions. Keep Confidence Level's **Reason** and **Not higher because** distinctions.

Do not replace emojis with later observed aliases on the assumption that observation means adoption. An exact heading check, semantic section-coverage check, source-truth check, and owner-acceptance check answer different questions. Passing any one of them does not establish the others.

## Copy, fill, and adopt

1. Check the project's accepted template and designated history owner. Select the applicable profile explicitly; do not migrate an existing archive as a side effect of writing a session.
2. Read the [full writing method](write-session-summaries.md). The [preserved full guide](../references/session-summary-v1-full-guide-sanitized.md) supplies additional original-derived examples and methodological detail. Its historical examples do not grant current authority.
3. Copy the selected blank artifact directly. The multi-project template begins with the Session title and contains two complete project blocks, an index, and a handoff. Duplicate or remove whole project blocks to fit the actual session. Re-number the index, project headings, and handoff consistently. One real project is valid if the project already uses this wrapper; do not invent another to fill the template.
4. Replace every placeholder with supported content, remove unused optional sections and unused contributor rows, and scale explanatory depth to the session. Keep all required section identities. If no material decision, adjustment, mistake, or open question occurred, say so briefly.
5. Replace every example anchor token with a unique session-specific identifier and update every matching link. The token `session-yyyy-mm-dd-a` is deliberately a placeholder, not a safe reusable identifier.
6. Put the new entry after any existing file/project indexes and before older session entries. Update the relevant indexes and retain earlier entry bodies intact.
7. Check the saved destination: heading levels, emoji identity, links, ordering, completeness, evidence boundaries, and actual readability. Saving, publishing, destination readback, and adoption are separate states.
8. If a format change is approved, record which profile, optional extensions, destination, navigation convention, and effective date were adopted in the project's Methodology or instructions owner. Adoption does not retroactively rewrite history or imply a system-wide release.

A new cumulative document may start directly with its newest Session heading, or use a deliberate lightweight index. Do not place a release-package introduction, instruction wrapper, or archive-migration divider ahead of the actual history just because a template came from a pack. Template instructions belong in this guide; actual session context belongs in the entry.

## Depth is responsive, structure is deliberate

The thirteen sections are a set of memory responsibilities, not a demand for identical paragraph counts. A small but substantive topic can have a few honest lines under several headings. A consequential session may need a long Actions chronology, developed insights, alternatives, decisions, friction, corrections, and a carefully bounded continuation path. Do not merge sections to manufacture brevity or pad them to manufacture depth.

Use H5 descriptive blocks inside multi-project core sections when a meaningful sequence needs them. Number work blocks in actual order, preserve uncertainty if timing is unknown, and explain turning points. A single continuous session may cross midnight. Grouping by project must retain the meaningful sequence within each project; cross-project dependencies can be stated in the session index and handoff without rewriting every project's chronology into one stream.

Preserve public rationale: what alternatives were considered, what evidence changed understanding, why an approach was rejected, what the owner actually decided, and what remains provisional. Do not manufacture private thought, a transcript, emotions, or certainty. The initial Session Goal must remain the initial intention, with later evolution labeled.

Each section should earn its own content. Actions describe events and sequence; Insights explain meaning; Decisions identify actual choices and status; Friction explains difficulty; Adjustments show changes of direction; Mistakes/Risks preserve consequential errors and risks; Current Position fixes the dated endpoint; Next Steps and handoff give a permitted re-entry path. Session Outcome explains what changed overall. Linking an execution report or incident record does not remove the need for enough local explanation to understand the session.

The multi-project candidate retains the established optional labels **📚 Files / Documents Created or Updated**, **🤖 Codex Work Performed**, and **🧪 Validation / Testing**. It also makes the full historical guide's **🗂️ Documentation Updates Needed** and **🚫 Deferred Work** available. None is mandatory. The single-project candidate uses generalized artifact and collaborator wording and an optional Starting State; those are identified portable refinements, not exact historical labels imposed on this wrapper.

## Time, identity, and role provenance

Record only supported metadata. “Not recorded,” “Not measured,” and “Unknown” are useful facts. A date range is not continuous active work, a pause is not labor, and an inferred start is not a recorded clock time. If measured active time is available, state the work blocks and exclusions. Do not turn a historical optional approximate-hours field into fabricated precision.

Separate identities by actual role and work block: coordinator, executor, reviewer, and documentation editor or reconstructor. A reviewer might inspect only an artifact, and an editor might reconstruct work they did not execute. Remove unused rows instead of inventing participants. When someone filled several roles, say so without pretending there were independent reviews.

Use these provenance labels explicitly:

| Category | What may be claimed | Required boundary |
| --- | --- | --- |
| Confirmed task configuration | A specific recorded configuration for the relevant task/work block | Name the record and scope. Configuration alone is not independent backend, billing, or performance proof. |
| Owner-selected / owner-reported | The owner selected or reported a setting or identity | Attribute the statement. Do not silently upgrade it to tool-verified configuration. |
| Owner-observed identity | The owner observed a displayed label or identity in a particular interface or moment | Record the observation and its limit. It does not verify every contributing task. |
| Unknown / not recorded | Evidence does not establish the model, effort, role detail, or timing | Leave it unknown; do not borrow a neighboring task's settings or guess from writing style. |

A reconstruction identifies the period covered, the actual evidence basis and cutoff, the later preparation date if known, and the editor/reconstructor's role. Preserve gaps and conflicting sources. A model named in a historical document is an attributed source claim until the relevant identity is supported; documentation authorship is not execution provenance.

## Newest-first history, indexes, and unique anchors

Session entries follow existing indexes in newest-first order. Use the latest supported checkpoint of each session as the ordering basis; do not promote an old reconstructed session merely because it was written today. If the source does not establish the relative order, mark that uncertainty rather than inventing a timestamp. Preserve chronological action order within each project block.

Two index layers may coexist:

- An archive-level index lists dated sessions, newest first, and links to their stable session anchors.
- A session's Projects covered index lists its numbered projects and links to the project anchors inside that entry.

Every explicit anchor is unique throughout the cumulative archive, not merely within the newly copied entry. A practical scheme is a date plus a stable disambiguator, followed by `project-index`, `project-1`, and `handoff` suffixes. The disambiguator distinguishes sessions on the same date; it is not a claim of precise timing. Do not renumber existing anchors just because an older session moves down the archive. Existing stable IDs and incoming links should survive ordinary additions.

The supplied template's two project anchors, index anchor, session anchor, and handoff anchor are internally consistent. Replace the shared session token as one operation, then check all links. After copying another project block, assign a fresh project suffix and update its title, end marker, index entry, and handoff. Duplicate project anchors are an error even when a renderer seems to navigate somewhere plausible.

If the destination does not preserve raw HTML anchor IDs, use its verified native block/heading links and maintain equivalent unique navigation. Markdown-to-app import, duplicate heading slugs, and emoji normalization vary by renderer. Preview and click the actual saved links; do not claim portability from a local text check alone.

An ordering repair moves intact entry bodies after a recoverable baseline has been established and verifies retention. It is not a reason to reword old conclusions. An old “waiting for review” is valid historical state even after a later entry records review. Correct a genuine error visibly and with a date, original claim, supported correction, and basis. Do not make later knowledge look contemporaneous.

## Compatibility and ownership

The profiles share the thirteen core responsibilities and detailed writing method; their heading depth and packaging differ. A new project can choose either suitable form. An existing project should keep its adopted profile unless an authorized change is made. The original H3 skeleton and explanatory H2 guide are preserved references, not mistakes to normalize away.

The session's Current Position is current **at its own stopping point**. A live Current State or Continuation owner may later contain a newer truth. Before executing Next Steps, reconcile current authority, the live checkpoint, and applicable evidence. A session recommendation cannot resume paused work, extend a completed Goal, authorize another project's work, or convert a proposal into acceptance.

Session history owns dated chronology and reasoning evolution. Architecture owns enduring structure; Roadmap owns phased direction; Methodology owns adopted working practice; decisions, failures, execution, evidence, and acceptance have their assigned owners. Keep sufficient local context to re-enter, and link the owning detail instead of copying a closing paragraph across every document. The destination application alone does not determine authority.

## What is preserved and what is new

**Preserved source material:** the complete supplied sanitized full guide, exact generic quick-skeleton text with its supplied provenance comment, and sanitized established wrapper are retained unchanged under [references](../references/README.md). The full guide includes its original-derived purpose, seven writing rules, detailed section explanations, examples, optional sections, quick skeleton, and closing principle. They have not been replaced by empty headings or rebranded as new universal originals.

**Preserved multi-project contract:** H1/H2/H3/H4/H5 responsibilities, numbered projects and navigation, the provenance block before the exact thirteen core headings, Before/After/Current standing, Reason/Not higher because, optional Personal Note, and per-project endpoints.

**New candidate expansion:** two fully prompted blank project blocks; explicit measured-time and evidence-cutoff fields; four-way provenance distinctions; conditional reviewer/editor attribution; reconstruction disclosure; prepared/saved/published/read-back/accepted distinctions; bounded next actions; unique-anchor prompts; and an expanded per-project handoff. These additions make the existing wrapper usable without pretending they were all present word-for-word in the source skeleton.

**Modern guidance alongside source history:** current-authority reconciliation, evidence-specific confidence, measured active time, meaningful near-miss assessment, and scoped maintenance apply to the candidate. Source examples about tool selection, full-log rewriting, and design-stage incidents remain examples. The [reference boundary notes](../references/README.md) explain the tension explicitly rather than silently editing historical text.

## Review checklist

- The intended profile and destination are explicit; existing project adoption is respected.
- Every real project block has the exact provenance heading followed by all thirteen core headings in order and at H4 for the multi-project profile.
- H1/H2/H3/H4/H5 responsibilities are preserved; optional sections do not replace required ones.
- Chronology, alternatives, friction, adjustments, actual outcomes, and uncertainty have enough meaningful depth.
- Metadata is supported; provenance distinguishes actual roles and work blocks; reconstructions are disclosed.
- Current Position is dated; Next Steps and handoff preserve each project's endpoint and current authority boundary.
- New entries are after indexes and before older entries; historic bodies are preserved.
- IDs are unique across the destination archive; index/back/handoff links are updated and tested in the actual renderer.
- Privacy, exact structure, semantic completeness, source truth, destination readback, and acceptance are checked separately.
- Historical source references remain visibly historical; candidate additions are not claimed as exact recovered originals or an adopted stable release.
