# 📘 Write Session Summaries

## What this document owns

This is the writing method for a full Session Summary: durable, dated project memory that preserves what happened, why it mattered, how understanding changed, and exactly where to resume. Use the [single-project Session Summary](../../../assets/templates/session-summary.md) or the [multi-project Session Summary](../../../assets/templates/session-summary-multi-project.md) as the copyable artifact. Choose its explicit [format profile](session-format-profiles.md) before writing; source hierarchies differ. Copy its Markdown into the project's chosen history owner, replace placeholders with supported content, and remove unused optional sections.

The intended reader is a returning human or collaborator who should not need to reconstruct the entire conversation. The author is the person or agent with access to the actual session record. A coordinator may integrate several contributors' work, but must preserve attribution and distinguish their returns from reviewed, accepted whole-project results.

Write a new entry after a substantial discussion, meaningful work block, milestone, recovery, change in direction, or handoff. Do not create another entry merely because a timer elapsed. Update the writing method only when its methodology or adopted format changes, not whenever project state changes.

## The identity to preserve

The preserved base has a Session title, thirteen required content sections, and an optional Personal Note. The required identities are:

1. 📘 Session title
2. 🕒 Time
3. 🎯 Session Goal
4. 🛠️ Actions Taken
5. 🧠 Key Insights
6. 📌 Decisions Made
7. ⚠️ Difficulties / Friction
8. 🔧 Adjustments Made
9. ❌ Mistakes / Risks Noted
10. 📍 Current Position
11. 🔜 Next Steps
12. ❓ Open Questions
13. 🧾 Session Outcome
14. 🔍 Confidence Level

💬 Personal Note is optional in the original base. Other optional sections have different origins:

| Section in the portable derivative | Origin and deliberate treatment |
| --- | --- |
| 🤖 Models, Effort, Roles and Provenance | Later multi-project practice, made available in both candidate profiles. Distinguishes actual roles, configured/reported/observed/verified identity and reconstruction limits. It is outside the original thirteen-section core. |
| 🧭 Starting State | A later project-specific v2 refinement, retained here as optional for re-entry, long or multi-day sessions. It is absent from the original v1.0 base. |
| 📚 Artifacts / Documents Created or Updated | Generalizes original optional “📚 Files / Documents Created or Updated” and later v2 artifact/platform wording. The role is preserved; the heading is a portable derivative. |
| 🤝 Collaborator Contribution | Later v2 refinement generalizing the original optional “🤖 Codex Work Performed.” It adds attribution and integration status across collaborators. |
| 🧪 Validation / Testing | Original optional extension, retained with more explicit evidence applicability. |
| 🗂️ Documentation Updates Needed | Original optional extension, retained. |
| 🚫 Deferred Work | Original optional extension, retained. |

These extensions are removable; they are not newly mandatory parts of the original base. The v1.0 heading **❌ Mistakes / Risks Noted** is preserved exactly, even though a later project-specific v2 used “Mistakes / Near-Misses.” Near-misses can be described under the preserved heading.

Retain every required section. If there was no material decision, adjustment, mistake, or question, say so briefly; do not manufacture content. A small entry can be concise inside this structure. A long session may need substantial prose and descriptive subsections. A compact checkpoint or Execution Summary is a different artifact, not an abbreviated replacement for this method.

This candidate single-project blank uses an H1 title and H2 core sections. The original quick skeleton uses H3; the established multi-project wrapper uses H1 session, H2 project, H3 session-level metadata/navigation/handoff, H4 provenance and core sections, and H5 chronology. Preserve a project's adopted profile rather than declaring one layout universally latest.

The title may be long enough to identify several important themes. Do not rename the established sections into a generic dossier or substitute a six-heading recap. Use the template's heading levels consistently; descriptive work-block subheadings belong underneath a core section.

## Who owns which truth

- Session Summary owns dated chronology, reasoning evolution, corrections, temporary context, and the end-of-session re-entry snapshot.
- [Current State](../../../assets/templates/current-state.md) owns the project's current orientation at the granularity assigned to it. Some projects need a broad phase snapshot; others need more frequent operational state. Decide that explicitly in the [source ownership map](../../../assets/templates/source-ownership-map.md).
- [Continuation State](../../../assets/templates/continuation-state.md) owns immediate recovery state where the project uses a separate continuation record.
- Architecture owns enduring structure; Methodology owns adopted working practice; Roadmap owns staged direction and advancement conditions.
- [Execution Summary](../../../assets/templates/execution-summary.md) owns concrete execution detail. Evidence and acceptance records own applicable checks and actual acceptance decisions.
- [Decision Record](../../../assets/templates/decision-record.md) owns a consequential choice's rationale and status; [Failure Intelligence](../../../assets/templates/failure-intelligence.md) owns qualifying incidents and prevention controls.

The canonical owner is chosen per question and project, not per application. A live database may be the correct operational owner. The summary can describe its dated observed state without claiming to replace it. Link durable content instead of copying entire other documents. Keep enough explanation locally to make the session intelligible if the reader has not yet followed the link.

## Build the entry from evidence

1. Read the actual work and conversation in order. Gather prior state, meaningful attempts, decisions, outputs, corrections, and the exact stopping point. Do not rely only on the final answer or a worker's success claim.
2. Identify what was directly observed, user-reported, inferred, proposed, decided, attempted, saved, published, read back, tested, and accepted. Use those verbs accurately.
3. Separate original intention from discoveries. Reconstruct the reasoning path without pretending the eventual answer was obvious at the start.
4. Write the chronological Actions first if useful. Then extract insights, decisions, friction, adjustments, and mistakes without copying the same paragraph into every section.
5. Write Current Position and Next Steps as a practical recovery test. A new collaborator should know what to open first, what is already done, what needs checking, and what requires authority.
6. Complete metadata and confidence from actual evidence. Unknown values stay unknown. An approximate contextual start is acceptable if labeled; invented clock time or model identity is not. Active time requires measured work blocks and stated exclusions. Wall-clock gaps are not active effort.
7. Check scope, chronology, attribution, and the destination. Follow [controlled maintenance](maintain-without-drift.md) when updating an existing cumulative record. Confirm the new entry is saved and readable before reporting publication as complete.

A source receipt can support this work, but must not become the summary's organizing voice. Avoid archive revision wrappers, migration manifests, artificial “preserved archive” dividers, and packaging metadata. If migration itself was the subject of a session, explain it as actual work inside the normal sections.

## How to write each section

### 📘 Session title and 🕒 Time

Identify when, which project, and the main themes or outcome. Metadata should orient, not carry the whole narrative. Record coordinator, executor, reviewer and documentation editor separately when they differ. Distinguish confirmed task configuration, owner-selected/reported settings, owner-observed identity, independently verified identity and unknown; one does not prove the others. A later reconstruction states its covered period, evidence cutoff, actual read scope and editor role. Do not project the editor's model onto earlier work. Mixed or uncertain identities remain mixed or unknown. Distinguish a date range from continuous labor. Explain why this is a useful stopping point.

### 🎯 Session Goal

Write a short framing paragraph followed by concrete intentions if useful. Include the starting problem, why it mattered, and the intended stopping condition. If the goal changed, explain the evolution explicitly. Do not list all completed actions as though they were the original goal.

### 🛠️ Actions Taken

Preserve the sequence of real work. Long sessions benefit from numbered, descriptive work blocks. Explain what was inspected, changed, attempted, compared, rejected, recovered, or verified. A failed publication attempt followed by a local draft must remain two events with different outcomes. A collaborator's report must remain attributed until integrated.

Sequence is often more useful than a mechanically complete tool log. Include enough detail to understand important branches and recover work, but link repetitive command outputs or test logs to their execution owner. When several sessions overlap, identify the ordering uncertainty rather than inventing a precise timeline.

### 🧠 Key Insights

Explain what the work taught: the insight, why it matters, and what it changes. This is not a second action list. Distinguish a strong local observation from a proposed general principle. If a useful insight has not been adopted as policy, leave it as an insight.

### 📌 Decisions Made

Record concrete choices with confirmed, provisional, deferred, or rejected status where useful. Identify the decision owner and material conditions. Preserve alternatives and the reason for not taking them. An agent's recommendation is not an owner decision; technical implementation is not approval. Link a separate decision record when future work depends on the choice's full reasoning.

### ⚠️ Difficulties / Friction

Write calmly about what was confusing, constrained, contested, or hard to use. Include relevant frustration when actually expressed, without manufacturing feelings or defending the assistant. Friction may explain why the course changed even when no failure occurred.

### 🔧 Adjustments Made

Use “shifted from / to / because” for significant changes of framing or method. Show the consequence for actual work. This section protects a future reader from reviving an early idea simply because they do not know why it was abandoned.

### ❌ Mistakes / Risks Noted

State what went wrong or nearly went wrong, actual versus potential impact, whether the correction was checked, and whether a Failure Intelligence record is warranted. A normal revision, temporary tool error, or untested concern is not automatically a consequential incident. Do not assign blame, model identity, data loss, or financial harm without evidence.

### 📍 Current Position

This is the strongest re-entry anchor. Contrast the relevant before and after states, then state exactly where work stopped. Label candidate, saved, verified, and accepted states accurately. Point to the live owner for volatile facts. The summary's current position means “current at this session's end,” not “permanently current.”

### 🔜 Next Steps

Give a short ordered path. Name the first document or artifact to read, the first check, the next bounded action, and the approval or dependency when needed. State what should not be rebuilt or reopened. A recommendation to continue does not extend a completed Goal or authorize a new project.

### ❓ Open Questions

Use real questions, not filler. Identify who or what can answer them and what depends on the answer. Fresh evidence, an external reply, and an owner decision are different dependencies. Do not infer an answer merely to make the entry sound finished.

### 🧾 Session Outcome

Close narratively: what changed, what became clearer, what was prevented, what was intentionally unfinished, and what is now possible. This is the meaning of the work rather than a replay of every action. A productive session can end with an unresolved question or a justified stop.

### 🔍 Confidence Level and optional 💬 Personal Note

Tie confidence to evidence and limits. Split it when, for example, the prepared artifact is well verified but deployment is unknown. Do not let high effort or a clean narrative inflate certainty. A personal note is useful only when authentic human meaning was expressed or directly relevant; never invent an emotional conclusion.

## Cumulative history and corrections

New dated entries go above older entries: newest first. Preserve chronological order within each entry. If an execution or discovery date differs from when the summary was written, make that clear.

Do not rewrite earlier sessions to make later knowledge look contemporaneous. An old “waiting for review” can remain true as historical state even after review happens. Record the later result in the later entry and link it if needed.

If an old entry contains a factual error rather than merely dated truth, make a visible dated correction identifying the original claim, supported correction, and basis. Do not silently falsify the history. Keep stable anchors where practical. Any broader migration or historical cleanup needs its own scoped process and a recoverable baseline; normal summary writing is not permission to rewrite the archive.

A new cumulative history can begin directly with its newest Session heading. Do not add a release-package wrapper to the historical document. Pack-level version and provenance belong in the pack's release materials.

## Worked example: a bounded catalog-help session

The following is a fully hypothetical teaching example using a fictional reading-room catalog and synthetic records. It is separate from the blank template. No event, approval, test result, or person below describes a real project.

### 📘 Session: [Illustrative date] — Reading-Room Catalog — Help Draft and Search-Label Review

#### 🕒 Time

Date: not specified in this teaching scenario. Start and end times: not recorded. Session type: review and drafting. Stage: internal prototype. Contributors: project owner and drafting assistant. Model: not recorded. Active time: not measured. Reason for summary: a reviewed draft is ready for a separate publication decision.

#### 🎯 Session Goal

The owner asked for a help-page draft explaining how volunteers could find a catalog item and interpret its availability. The intended stopping point was a reviewable draft checked against six synthetic records. Publication and changes to the underlying catalog were outside this session's scope.

#### 🛠️ Actions Taken

1. The assistant read the existing label definitions and the six-record test packet. It initially treated “available” as meaning that an item was ready for immediate collection. The source definitions instead meant that it was eligible for a reservation request; collection still required staff confirmation.
2. Two draft approaches were compared. A field-by-field glossary preserved every detail but made the first practical action hard to find. A short task sequence put search, selection, and reservation first, with a small glossary below. The owner chose the task sequence for the draft.
3. The help text was tested against all six synthetic records. Five examples were explained clearly. The sixth used a legacy label with no definition in the packet. The assistant did not guess its meaning or alter the record; it marked that example unresolved and asked for the label owner to confirm it.
4. The revised draft was saved and reopened. Its wording included the reservation-versus-collection distinction and the unresolved legacy-label note. No live page was published and no operational catalog record was changed.

#### 🧠 Key Insights

The most important wording problem was semantic, not stylistic. A concise but wrong “ready to collect” instruction could send a volunteer to the wrong next action. The task-first layout improved the reading path, but it did not remove the need for authoritative definitions.

The six examples were useful coverage of this packet, not proof that every catalog state had been tested. The unresolved legacy label exposed a limit in the source definitions rather than a reason to invent a complete answer.

#### 📌 Decisions Made

- Confirmed by the owner: use the task sequence as the draft's main structure, with the glossary below.
- Confirmed for this draft: describe “available” as eligible for a reservation request; preserve the separate collection-confirmation step.
- Deferred: publication, pending the missing label definition and owner review of the final wording.
- Rejected: hiding the unresolved example to make the draft appear fully verified.

#### ⚠️ Difficulties / Friction

The first glossary draft was accurate in several details but interrupted the volunteer's likely reading path. The legacy label could not be resolved from the supplied sources. Those two problems required different remedies: a layout change for the first, authoritative clarification for the second.

#### 🔧 Adjustments Made

Shifted from a field-by-field reference to a task-first help page because the practical entry point was hard to see. Shifted from assuming ordinary-language meaning for “available” to using the project's explicit definition because the label had a narrower operational meaning.

#### ❌ Mistakes / Risks Noted

The early wording incorrectly implied immediate collection. It was corrected before publication, and no volunteer received that instruction. The potential impact was a wasted collection trip. This isolated drafting error is preserved here; a separate incident record would be warranted if it revealed a recurring consequential labeling defect.

#### 📍 Current Position

Before the session, the catalog had label definitions but no task-oriented help draft. After the session, a saved and reopened draft explains five test cases and explicitly flags one unresolved label.

Current standing: the internal draft is ready for the missing-definition check and final owner review; publication remains pending.

The live catalog remains the operational owner. This entry records only the end-of-session state.

#### 🔜 Next Steps

1. Open the draft's legacy-label note and obtain the definition from the label owner.
2. Check the sixth synthetic case against that definition and revise only the affected explanation.
3. Ask the project owner to review the final draft and decide whether to publish it.

Do not rebuild the task sequence or change catalog records as a side effect of finishing the help text.

#### ❓ Open Questions

What does the legacy label mean, and is it still in active use? The label owner must answer before the draft can claim coverage of all six cases. Publication needs a separate owner decision.

#### 🧾 Session Outcome

The session produced a usable internal help draft and corrected a misleading interpretation before it reached readers. It also made the evidence boundary visible: five examples were explained, one remained unresolved, and nothing had been published. The next session can resolve that single gap instead of restarting the whole page.

#### 🔍 Confidence Level

High confidence that the saved draft matches the five resolved examples, because it was compared with the packet and reopened after saving. Limited confidence in complete label coverage, because one definition is missing and no broader catalog audit was performed. No publication claim is made.

## Final quality check

- Can a reader recover the sequence, rationale, rejected paths, friction, corrections, and actual outcome?
- Are all required identities present, with depth proportional to the real session?
- Are observations, inferences, recommendations, decisions, attempts, successful writes, readback, and acceptance distinguishable?
- Are time and model metadata supported, and contributor credit accurate?
- Are historical truth and live ownership separate?
- Is the first continuation action concrete and inside the correct authority boundary?
- Is the entry newest-first without rewriting older history or introducing archive packaging?

## Lineage and deliberate changes

This portable method is derived from the original Session Summary Template v1.0 and later project-specific v2 refinements. It preserves the full emoji identity, re-entry purpose, reasoning path, selective optional sections, and permission for substantial depth. The original “Mistakes / Risks Noted” identity is retained while also covering near-misses.

The portable derivative replaces named people, platforms, and project details with roles and project-chosen owners; adopts newest-first cumulative entries; tightens time/model attribution; and makes preparation, save, readback, acceptance, and continuation boundaries explicit. It is an authored derivative, not a byte-for-byte rendering of the escaped original Markdown. Original source documents are not overwritten or retroactively versioned by using this template.
