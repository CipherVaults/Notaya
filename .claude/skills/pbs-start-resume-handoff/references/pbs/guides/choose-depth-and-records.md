# 🗂️ Choose depth and records

## 🎯 Start with the cost of losing understanding

Ask what would become difficult or unsafe if the current conversation disappeared. Preserve those answers. Do not create a permanent document merely because the library contains a template.

Use three independent judgments:
1. **Persistence:** one result, or continuing work?
2. **Complexity:** one clear path, or interacting parts and evolving decisions?
3. **Consequence:** easy reversal, or costly/private/external/irreversible effects?

A short action can have high consequence. A large archive can be low-risk to read. Document count should not be a proxy for either.

## 🪶 Bounded task

Use when the owner wants one clear answer or artifact, the scope is already understood, and the result is easy to inspect.

Usually sufficient:
- the actual instruction or a short Task Brief;
- a result and its scoped verification;
- a short execution report/checkpoint if future recovery matters.

Do not make the user establish a new project hub for every task. If a meaningful learning or decision session occurred, use the full Session Summary method at an appropriate depth. A checkpoint is not a renamed abbreviated Session Summary.

## 🌱 Continuing project

Use when work will span several sessions, goals or decisions.

Usually keep:
- a project entry and source map;
- Architecture or a clear project-purpose section;
- Current and the current Goal/task;
- a Plan or Roadmap appropriate to the work;
- Session/decision memory;
- a recoverable next step.

Combine clear owners in one page when they remain easy to find. For example, a small research project can keep its Goal, Plan, evidence and acceptance in one working record with labeled sections. The responsibilities remain distinct even without separate files.

## 🏗️ Substantial autonomous or consequential work

Separate owners when combining them would hide authority, evidence, progress or recovery.

Common additions:
- explicit Goal and adaptive Plan;
- Evidence and Acceptance;
- Continuation separate from accepted Current;
- dated Execution Summaries and an index;
- durable worker contracts/returns if work is delegated;
- version checkpoints and separate preservation when the loss consequence warrants it;
- independent review when the risk or uncertainty justifies it.

A broad Goal can permit ordinary in-scope work without requiring approval for every minor implementation detail. It cannot override the executing environment's safety and confirmation rules.

## 🔬 Specialist complexity

Add a specialist record only when a real question no longer fits its existing owner:
- **Technical Reference:** implemented mechanisms, contracts or reproduction steps are too detailed for Architecture.
- **How This Project Works:** a curious non-participant needs an end-to-end explanation.
- **Inventory:** changing tools, assets, versions or capabilities must be tracked with dates.
- **Experiment Log:** actual trials and their interpretation matter over time.
- **Security:** threat boundaries, permissions or sensitive-data handling need a distinct explanation.
- **Testing:** verification design and recurring coverage have become a reusable system.
- **Benchmarking:** measurement conditions, variability and interpretation need their own owner.

Do not create a Technical Reference before there is an implemented mechanism to explain unless the document is clearly a design proposal.

## 📚 Question-to-owner catalog

| Question | Primary owner | Change trigger | Avoid |
|---|---|---|---|
| What is this and how do I enter? | README / project home | Entry route, purpose or usage changes | Duplicating the whole library |
| What sources own which facts? | Source map | Authority, storage or source ownership changes | Treating latest timestamp as authority |
| What is the durable structure? | Architecture | Components, boundaries or enduring relationships change | Current task/collaborator status |
| How do we work repeatedly? | Methodology | A recurring method is adopted or revised | Dumping all examples/history |
| Where could the project go? | Roadmap | Phase strategy or exit boundary changes | A second live task dashboard |
| What may be pursued now? | Goal / Task Brief / explicit bounded request | New authorization or approved amendment | Silent scope expansion |
| How will this Goal be pursued? | Plan | Strategy/dependency changes | Copying or weakening the Goal |
| What was observed? | Evidence | Material observation/check/artifact | Unsupported success narrative |
| Which claims are accepted? | Acceptance | Applicable evidence and decision change | Treating pass as owner acceptance |
| What is true now at the chosen granularity? | Current, pointing to the assigned live operational owner | Verified state, acceptance, blocker or authority change | Unlabeled promotion of partial/unaccepted work or a duplicated dashboard |
| What exactly survives and comes next? | Continuation | Material checkpoint/interruption/handoff | Unquestionable stale prose |
| What did execution do? | Execution Summary | Meaningful work cycle/milestone | Full strategic/emotional history |
| How did understanding evolve? | Session Summary | Substantial session or meaningful continuity need | Generic recap or machine receipt |
| What did we choose and why? | Decision record | Consequential choice/revisit | Promoting suggestions to decisions |
| What went wrong and how to prevent recurrence? | Failure Intelligence | Consequential incident or changed diagnosis | Every inconvenience or unrelated failure |

## 🔧 Combining and splitting

Combine records when:
- the work is small;
- readers can still distinguish authority, observation and acceptance;
- updates remain manageable;
- no one has to maintain the same fact in two places.

Split when:
- a separate question has a clear reader or owner;
- history and live state are becoming mixed;
- frequent changes make a durable reference unstable;
- navigation or file size prevents reliable re-entry;
- different access boundaries require separation.

A split is a migration: record what moved, preserve history/links and verify the new ownership. It is not permission to rewrite historical truth.

## 🧭 Mode is a working arrangement

- **Coordinator-led:** early discovery and decisions benefit from a dedicated reasoning home.
- **Direct executor:** the executor is the main workspace; scope may be a small task or an established project.
- **Iterative hybrid:** reasoning and execution repeatedly inform each other.
- **Retrospective documentation:** useful execution happened first and now needs explanation, integration or durable memory.

The older word “Hybrid” covered both of the latter patterns. Name the actual arrangement instead of forcing the project into ambiguous terminology.

## ✅ The proportionality test

Before adding a record, answer:
- What question will it own?
- Who needs it?
- What real event will update it?
- Where is this answer currently kept?
- What will be linked rather than copied?
- What breaks if we omit it?

If those answers are weak, keep the information in an existing owner.
