# PBS Start, Resume & Handoff

**PBS method version 1.1 — approved 26 October 2026.** Promoted from reviewed candidate.4 for project-development use. See [origin and compatibility](references/origin-and-compatibility.md) for the bounded evidence and remaining limits. Version approval does not grant project-specific authority.

Help the user start or recover bounded project work with visible authority, evidence and continuity. This is one local Codex adaptation of the confirmed Notion skill **Start, Resume & Handoff**, with nine lifecycle prompts. It belongs to **The AI Project Bootstrap System**. All essential method is bundled locally; a Notion connection is optional. Use the root and relevant bundled guides/templates without access to a private hub. Missing project facts, tools or permission remain real gaps; package availability does not supply them.

## Enter at the actual work boundary

**Environment-routing reference refresh · October 16, 2026.** For work dependent on an owner's computer, browser/desktop UI or a change of executor, read the full **Verify the execution environment** procedure in [How PBS works](references/pbs/guides/system-handbook.md) before dependent actions. Inventory read-only runtime facts, classify cloud / owner-local / unknown from evidence, then follow its route and stop conditions. Missing UI tools alone do not establish cloud execution. Here a local task/conversation is not a locally running AI model; file access, file writes, browser/session control and whole-desktop control are separate capabilities. Check connection, enablement, relevant authentication and operation permission separately. Messageability is not desktop capability. Carry still-valid approval forward, but never bypass a denial or repeat an unchanged known failure.

1. Read applicable project instructions and the smallest relevant source set. Identify the user's current request, still-valid authorization and later amendments or pauses. Preserve the project's adopted formats and source ownership; a familiar filename or newer timestamp does not establish authority.
2. For recovery, reconcile Current/Continuation, the active Goal or bounded request, relevant Plan and execution/session records against surviving artifacts. Classify accepted, complete-but-unreconciled, implemented-but-unverified, partial and unknown work. Preserve useful work and failed-attempt evidence before choosing the exact first permitted unfinished action.

   At a meaningful start, resume, amendment or handoff boundary, choose the next action from the effective authority, actual artifact and remaining evidence—not the last instruction-shaped line in an old log. Reuse the project's existing current entry and source owners; do not create a parallel current file or request routine reapproval. For contradictory entry routes, use the recovery procedure in [Govern, execute and recover](references/pbs/guides/govern-execute-and-recover.md).

## Carry authority forward accurately

The user's explicit bounded request may already authorize the work; a separate Goal file or repeated approval is not compulsory. Continue ordinary in-scope work under still-valid authority. A Plan proposes how; it does not grant permission. Pause dependent actions at an actual gate, explicit pause, material scope/acceptance change or essential capability block, while continuing useful independent authorized work.

For owner-adopted ordered milestones, close the current milestone before later implementation unless the applicable instruction explicitly permits reordering or parallel work. Apply the preparation and dependency-aware deferral boundaries in [Execute using an adaptive Plan](references/pbs/guides/govern-execute-and-recover.md#5-execute-using-an-adaptive-plan).

Installing or invoking this skill grants no blanket execution, publication, messaging, scheduling, migration or access permissions. Distinguish a prepared handoff from delivered, acknowledged, executed and accepted states. Confirm the recipient and access limits; do not assume another conversation sees local files. Follow the user's actual messaging and external-action authorization.

## Preserve the right records

- Choose depth by persistence, complexity and consequence. A compact Task Brief or existing record can hold several clearly separated answers. Create a document only when its owned question needs it.
- Keep Goal/authority, Plan/strategy, evidence/observation and acceptance/decision separate. Current records the accepted present at the project's assigned granularity; Continuation preserves exact unfinished or unaccepted work. Reconcile contradictions instead of flattening them.
- At substantive stops or re-entry, notice unexplained drift from the adopted record profile and stale current pointers. Use [Maintain without drift](references/pbs/guides/maintain-without-drift.md) for a bounded correction within authority; respect approved format changes and leave healthy or tiny-task records proportionate.
- Update only owners whose answers changed. Preserve sound passages, chronology, rejected options and user-visible reasons. Use links and purposeful dated summaries instead of copying one checkpoint into every document. Verify saved destinations, references and preserved history.
- Execution Summary records concrete work and checks. Session Summary preserves the session's evolution and continuity. A brief checkpoint is not a substitute for a substantive Session Summary.
- Use the project's established full Session format first. When a new candidate format is requested, select the exact single-project or multi-project asset. Preserve every core heading, emoji, order, hierarchy and chronology level; retain both full project blocks in the multi-project blank. Write honest short content for quiet required sections instead of deleting them. Depth may vary; structure must not silently drift.
- Record known time, roles/model/effort, reconstruction provenance, decisions and uncertainty without guessing. Preserve user context and friction relevant to the work and concise reasons for accepted/rejected options; never request hidden reasoning. Sanitize reusable examples and shareable outputs.

## Verify and leave a usable continuation

Tie checks to actual artifact identities and effective criteria. When the result is consumed through navigation, packaging or derived layers, use [Validate the actual use path](references/pbs/guides/govern-execute-and-recover.md) to derive the relevant end-to-end operation instead of relying only on producer checks. Keep outcome, applicability and acceptance independent; label historical, not-run, inconclusive and unavailable evidence. A saved file, component test or worker completion does not establish integrated success or owner acceptance. Do not waive an unmet mandatory criterion without an explicit applicable amendment.

Finish with the concrete result, scoped evidence, remaining limits and exact next permitted action or decision. Stop at the satisfied bounded Goal; a useful successor idea does not authorize itself. Preserve the checkpoint if interrupted.
