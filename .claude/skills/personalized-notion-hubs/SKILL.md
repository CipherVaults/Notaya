# Personalized Notion Hubs

Make a familiar native workspace that helps Ahmed orient, choose, work, verify and resume. Adapt his existing method; do not impose a new universal dashboard. This instruction-only skill supplies design guidance, not credentials, a Notion connection or additional authority.

## Establish the task and live baseline

Identify the outcome, operation (new/adapt/polish), exact target, relevant sources, domain, known state/next action and preservation boundaries. Infer reversible layout details; ask only about missing facts or decisions that materially affect the result. Unknown state remains unknown, not invented progress.

Inspect the existing hub, Registry entry, canonical databases, saved views and relevant nested pages/record bodies before creating anything. Inspect properties as well as text: a blank reading-card body can be intentional. Reuse the intended hub rather than making a competing copy. Refresh project facts from current authorized evidence; old snapshot examples are not current project status.

Use the Notion connector actually available in this session, or a user-authorized browser route. Check fetch completeness and real capability before relying on it. If private access or a required native operation is unavailable, explain the exact limitation and offer an accurately labeled draft/specification; request exported source content when necessary. Never claim text headings are a database or board.

## Choose the smallest useful structure

Choose by purpose: an educational hub leads with a learning journey, lessons, practice and helpful visuals; writing leads with editable work; finance leads with its records and operating rules; evidence leads with findings. Use the relevant [layout recipe](references/layout-recipes.md); a software recipe never takes over these other jobs.

- **Home:** visible purpose, a useful first-use example and next action where needed, a direct return-to-work route, actual current position with evidence date, one explicit next action/gate, a short 60-second workflow and key field questions. Give collaborating AIs a clear operating-contract/continuation route when useful; these reader roles do not require extra pages. Keep active navigation visible; put richer dictionaries and operating rules in accessible lower native toggles.
- **Work:** by default, actual databases have separate child-page surfaces and Home uses navigation links without inline embeds. When Ahmed explicitly requests the optional software-project layout below, place the native milestone database/view inside Home using the same canonical source. Keep one canonical data source **per entity type**; linked views reuse it rather than creating duplicate datasets. Tasks, transactions, obligations and books are not one generic entity.
- **Working rooms:** only those that reduce friction. Drafting leads with editable work; planning leads with scope/gates; evidence keeps results/charts visible; handoffs lead with the stopping point. Small projects can combine rooms.
- **Reference/history:** preserve dated reasoning, source links and supersession without crowding daily work. A property-only reading/registry record can be finished.

A requested project hub is standalone. The Projects & Ideas Registry holds a linked reminder/classification entry, not the entire hub. Before moving an existing nested hub, check sharing inheritance and authorization; when permissions cannot be established, preserve placement and link instead.

Read [human entry and template reuse](references/human-entry-and-template-reuse.md) when first-use/return/AI journeys, reusable templates or a substantial restructure are involved. Preserve a source-to-destination/owner map of meaningful content and responsibilities; keep production receipts out of the reader's entrance. Reconcile required template identities and exact routes, then test findability separately from isolated copying/downloading.

When a long guide, research page or Plan has an overwhelming table of contents, put its native TOC inside a clearly labeled native toggle near the start, initially collapsed. Keep purpose, example, next action and short working/resume/AI routes visible; short navigation and a requested operative board stay visible. Preserve all headings/body and direct entrances, and check expansion/collapse plus representative heading links separately in the actual rendering when authorized access is available.

Read [layout recipes](references/layout-recipes.md) for the relevant page job and visual treatment. Read [entities and views](references/entities-and-views.md) when designing databases, adapting phases/properties or handling finance/reading/opportunities/software/R&D. Choose recipes, not a mandatory page count.

## Build or polish within authorization

Here **cards means native Board/Kanban**, grouped by a justified phase/status/category, unless Ahmed explicitly asks for Gallery. Choose the primary home link from the domain's daily work: a phase board can lead project tasks; an operational records system should lead with its capture/review/resume surface. Keep operational records separate from setup/development tasks; a setup board is primary only when setup is the actual requested work. Gallery is optional; current/next and full-data views use the same entity records on the chosen child-page or explicitly requested software-project inline surfaces. Retain a genuinely unfiltered full-data index; a filtered view called Default is not All.

Keep classification (phase/version/category/area/type), lifecycle/status, record quality, priority and evidence basis/freshness distinct. Explain the actual schema with exact property/option labels, meanings, inclusion/exclusion rules, examples and unknown/edge cases; explain saved views by their question and actual filter. Clearly separate proposed fields/options from implemented schema and synchronize the guide with schema changes. Read [entities and views](references/entities-and-views.md) for the dictionary contract; add fields only when useful.

Use native Notion hierarchy, restrained callouts, useful spacing and short labels. Emoji plus readable text are functional identifiers: use stable meaningful symbols consistently across options, properties, views and explanations. Preserve established labels; do not silently rename them or add arbitrary decoration. Colors supplement explicit words; red Area does not mean failure. Use columns only where readable and useful.

Preserve user edits, IDs, rich-text mentions, relations, formulas, attachments, evidence and meaningful history. Distinguish planned, source-reported, user-reported, observed/measured, accepted and unknown claims. Recent edit time is not evidence freshness. Explain source preservation, uncertainty, duplicate/update rules and who may change what for the actual domain. Do not promise automatic AI processing unless configured and verified. Creating a hub or planning content does not approve project execution, imports, future actions, spending or sharing.

For starter duplication, first establish the copy's owned database/data-source identity. Check/remap child mentions, view links, internal links and relations before editing copy records. Remove or retain visibly labeled demonstration records only within the authorized copy. Duplication/remapping of the source starter is **not yet tested**; never promise automatic remapping or a universal default tab.

Read [verification and operations](references/verification-and-operations.md) before live structural writes, duplication, moving pages or final acceptance. Inspect current tool schemas; do not hardcode stale connector names or infer capabilities from this skill.

## Verify and deliver

Read back the saved home/children, database schema, records and changed view settings. Verify the chosen placement: separate child-page databases/link-only Home by default, or the explicitly requested native inline milestone surface for the optional software-project recipe. Verify the domain-appropriate primary route, canonical identities, native types, groupings, displayed fields, sorts, exact filters, membership/pagination and working links. Check the visible workflow, lower native guide toggles, schema/proposal distinction and semantic emoji consistency against saved configuration. Confirm the full-data view is unfiltered; distinguish Notion-native archived/deleted objects from an Archived lifecycle category. A direct view link selects a view; it is not proof of global tab order/default.

When authorized visual access is available, inspect the home, primary work surface (including requested board/cards) and desktop/narrow navigation. For an explicit inside-Home software request, rendered acceptance is mandatory: actual native board columns/cards must appear on Home, intended tabs must switch that in-Home surface, and a representative card must open and return to it using the same canonical records. `inline=true`, child/source links, counts and saved configuration cannot pass this gate. An owner report that the board opens outside Home is a failed presentation result. If visual access is blocked, retain that failure or mark an untested presentation unverified and provide the [blocked-visual handoff](references/verification-and-operations.md); do not claim the layout is fixed. Keep configuration/source checks separate. Never create duplicate sources/cards as a blind repair.

Return the hub/main-view links, what changed and was preserved, evidence basis and remaining limitations. Separate semantic preservation, native structure, human findability, isolated reuse, rendered usability and owner acceptance; changed routes need their own destination checks. A blocked native operation stays explicitly unfinished even if a polished local draft exists.
