# Optional Software-Development Project Hub

**Revision: `2026-10-16.software-recipe.2` · owner-feedback correction.**

## Select this recipe deliberately

Use this layout when Ahmed requests an operative software-project Home with its milestone work surface inside Home, or explicitly chooses this recipe. A software-related title alone does not override another requested layout. The ordinary separate-child-page database pattern remains the default for other hubs, especially operational records systems. Do not retrofit existing hubs merely because this recipe exists.

## Operative Home

Lead with the project's purpose and a useful result, a short first-use example when needed, the real dated checkpoint, and one next action or decision gate. Give returning users a direct work route and collaborating AIs a route to the operating contract and continuation.

Place the requested **native inline milestone database/view inside Home**, with useful cards visible in context. A link to a child database alone does not satisfy an explicit inline request. Retain direct navigation to the full source, working rooms and deep research; a compact Home is not permission to shorten or discard the research.

## One source, complementary views

Choose what a milestone record represents before adding fields. Reuse one canonical source for those records across inline and full-page presentations. If an existing full-page database owns them, a linked inline view can expose that same source without copying records or moving ownership.

Useful views, when they answer real questions:

| View | Question | Contract |
| --- | --- | --- |
| Phase Board | Where does each outcome fit in the sequence? | Native Board grouped by the actual Phase field |
| Horizon or version Board | What is previous, current and future, or part of an evidenced release? | Same records, grouped by a distinct horizon/version field |
| Current gates | What needs attention or a decision now? | Explicit filters aligned with actual lifecycle/gate meanings |
| Full data | What exists outside the working queue? | Genuinely unfiltered table of the same canonical source |

Phase is sequence; horizon/version is placement; lifecycle is what is actually true. “Current design” is not a shipped release, and a prior recovery baseline is not an earlier release of new UX software. Use actual release versions only when evidence supports them. Keep proposed, partial, verified, accepted and owner-review-pending states distinct as the real project requires. Do not invent dates, percentages, completed work or approval.

View and card counts, option sets and release labels come from the project. Do not copy the examples' quotas or assume a view name proves its filter, global default tab or visibility.

## Meaningful cards and dictionary

Use stable meaningful icons plus readable labels, restrained colors and fields that help choose the next action: lifecycle, concise outcome, next gate, source/evidence and a relevant track where useful. Keep card displays readable; put full fields in the table.

A substantive software milestone card should explain why it matters, its intended or observed outcome, current evidence and limits, next gate, and governing source. It summarizes and routes; it does not become a second Plan or acceptance record. Lightweight reading or Registry records still need no invented body.

Explain the actual fields, exact options and each view's question/filter in an accessible dictionary. Distinguish classification, lifecycle, priority and evidence. Match implemented schema; label proposals honestly.

## Distinct rooms and source ownership

| Room or role | Owned answer |
| --- | --- |
| Architecture & Decisions | Enduring structure, boundaries, consequential choices and their status/rationale |
| Planning Ground / Roadmap | Current route, phases, dependencies, alternatives and exit gates |
| Current State, Evidence & Continuity | Dated standing, applicable results and limits, unfinished work and exact next permitted action |
| Specialist design/research rooms | Full requirements, investigations, worked examples and technical detail |
| Home and milestone cards | Orientation and concise linked summaries of those owners |

Combine rooms when useful, but keep the answers distinct. Map important source content to its exact destination and canonical owner, including caveats, responsibilities, examples and authority. Preserve full research through direct navigation and progressive disclosure. Keep production receipts available through a maintenance route rather than making them the reader's entrance.

For a long Plan, Human Guide or research room whose table of contents crowds the opening, place the native TOC in a clearly labeled native toggle that starts collapsed. Keep the short orientation, next action and direct work routes visible. This is purpose-appropriate progressive disclosure, not a rule to hide short navigation or the requested inline board. Preserve the full page and heading links; verify the toggle and representative heading routes in the rendered page when authorized visual access is available.

Keep related projects identifiable. For example, a reader UX/owned-software project can depend on backup evidence while backup capture and its acceptance remain owned by the separate recovery project and Registry card. A related baseline card links that evidence rather than taking over its state.

## Govern a bounded pilot

Use **Plan → review/amendment → approved bounded Goal → pilot QA → reviewed expansion**. Planning cards and native views do not authorize software, plugin installation, migrations or recurring work. Carry forward a still-valid approved Goal; a hub change alone does not require ceremonial reapproval.

When portability or owned tooling is part of the actual outcome, define source/build ownership, persistent data/configuration/assets/dependencies, supported versions and restoration steps before implementation. Include the agreed restore scenario in the first pilot and meaningful later checks; preserve a plain-content fallback where promised. Do not copy another project's entire technical contract.

## Verify the requested layout and claims

Read back the stored block representation, canonical source identity, Board types/groupings, fields, sorts, exact filters, full-data membership/pagination, substantive cards and links. This verifies configuration; it does not prove actual inside-Home rendering. Preserve existing records and history. Check that the summary, dictionary, Plan and continuation agree about authority and evidence.

Walk the real first-use, return, AI and template routes where relevant. Inspect rendered cards, wrapping, narrow-screen behavior and diagrams when authorized visual access is available. Connector readback, source-code preservation, rendered QA, isolated reuse, owner acceptance and real project execution are separate claims. Report exactly which occurred; a technically saved hub is not proof of visual usability or an executed pilot.

### Mandatory rendered acceptance for an inside-Home request

Acceptance requires the actual rendered Home to show native board columns and usable cards in context. Intended view tabs must switch that surface while the reader remains in Home; a full-page source link is supplementary. Confirm that the visible records are the same canonical records without recreating them.

Run these regressions on the real Home, through authorized authenticated visual access:

1. Open Home directly and capture the native board visible at its intended position after the introductory working context.
2. Switch the justified phase/horizon/current/full-data tabs. Verify that the working surface remains inside Home instead of navigating to an outside database page.
3. Open a representative card and return to the in-Home board. Check its source identity, evidence and unchanged record count; metadata alone cannot establish the interaction.
4. Check labels, cards and column access at relevant desktop and narrow widths. Record the actual surfaces/widths and scroll/overflow behavior; do not infer them from source code.
5. Distinguish the source-database link from the linked in-Home presentation. A child source, `inline=true`, direct-view links, saved configuration, counts and successful API writes are structural evidence only.

If the owner reports the board outside Home, record **presentation acceptance failed**. Preserve the independently supported source/schema/data checks separately; this does not establish a data failure. Physical repair remains pending until authorized inspection, repair and rendered recheck establish the requested behavior. Do not use a failed software fixture as a verified inline example or duplicate databases/cards to make a blind repair.

When visual access is blocked, use the [blocked-visual handoff](verification-and-operations.md): exact Home/source/view identities, owner report, known configuration evidence, actual access blocker and remaining desktop/narrow/tab/card checks. Coordinate an authenticated browser or owner screenshots without changing access/settings or claiming a repair. An unperformed check remains unverified; an existing owner-reported failure remains failed, not merely unverified.
