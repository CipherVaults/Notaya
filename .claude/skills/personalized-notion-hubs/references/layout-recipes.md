# Layout Recipes

Adapted from the October 11, 2026 Notion Hub Playbook and inspected nested examples. These are role-specific recipes, not pages to create automatically. Populate them from real inputs; no scaffold headings or fictional progress should remain in a delivered live hub.

## Home: Orient and Choose

Recommended reading order:

1. Purpose in one sentence: the outcome and why this workspace exists.
2. Main work entry: short, prominent route to the domain's daily work on the chosen surface. Use a phase/status board for project tasks when relevant; lead an operational system with the records it captures, reviews or resumes. Keep setup/development work a separate route.
3. Current position: what is actually true, evidence date, current focus and important unknowns.
4. Next action or decision: one concrete move, including approval/evidence needed.
5. Visible working navigation: a few short room names, one-line explanations only when useful.
6. A visible 60-second workflow and short field primer: the few questions a person must answer to use this system.
7. Accessible lower native toggles for the classification dictionary and shared human/AI operating rules, plus quiet reference/history access and an optional Registry link.

This ordering is adaptable; a current decision can sit beside the main entry. The first screen should answer what/where-now/what-next; do not bury active routes under methodology. By default, actual databases have separate child-page surfaces and Home uses navigation links without inline embeds. The explicit [optional software-project recipe](software-development-project-hub.md) instead places a native milestone database/view inside Home over the same canonical records; do not apply that exception to unrelated hubs.

A system should explain itself without a fixed wall of instructions. For example, a records workflow might be capture source → classify only what is known → review the relevant queue → record the next step; a project workflow might be choose a task → check its evidence/gate → work → leave a resume point. Adapt these, do not impose both. Match the lower dictionary to the actual schema using [entities and views](entities-and-views.md). Put source preservation, uncertainty, duplicate/update rules and human/AI responsibilities in the lower operating guide. Do not add empty taxonomy or mandatory extra guide pages.

Use a standalone project page when requested. Link it from the existing Registry's Key Link/Home/equivalent property, preserving the reminder entry's classification. Do not move a live Registry-body hub just to conform: inheritance and human direction govern relocation.

For Edition 3 first-use/return/AI journeys, exact template routes and semantic preservation, read [human entry and template reuse](human-entry-and-template-reuse.md).

For the expressly requested software inside-Home option, actual rendered native board columns/cards, in-Home tab switching and card open/return are mandatory acceptance checks at desktop/narrow widths. Stored inline metadata is insufficient; a blocked check does not pass, and an owner-reported outside-Home board remains failed pending physical repair and rendered recheck. Follow the detailed recipe and [visual handoff](verification-and-operations.md), preserving one canonical source and its records.

## Planning: Scope and Gates

Lead with purpose, current baseline/maturity and planning-only scope. Follow with chosen direction/ordered sequence, useful work tracks, evidence gaps and decisions/approval gates. Keep earlier dated rationale separate or collapsed and identify what supersedes it.

Keep chosen, proposed, observed and historical material distinguishable. Real versions are appropriate for releases, not generic room names. A planning page or critical-priority label is not approval to execute.

Example pattern: FFmpeg's planning ground keeps current direction above retained earlier rationale. Copy the organization, not its release labels or engineering requirements.

## Substantial Work Card: Summarize and Route

Open with actual lifecycle and evidence basis. Then: why it matters, intended/observed result, relevant scope/conditions, next gate/action and canonical governing source. Keep a short card useful; link to large evidence or the authoritative plan rather than maintaining a second one.

An experiment in a Next column is not running. A proposed outcome is not a measured result. A software feature card labeled Critical planning is not delivered or authorized implementation.

## Drafting: Open Onto the Work

Put the current editable writing/build area first. When useful, distinguish raw contribution/refinement from the best current assembled output. Keep a compact review checklist nearby. Requirements/reference can be a neighboring page/tab, not a wall of methodology before the writing.

Create extra proof/test/questionnaire pages only when substantial work actually benefits. Preserve a submitted/final version separately from later practice. Do not duplicate opportunity economics, relationship state or outcome tracking from its canonical Registry.

Example: the Freelancing Arc's Workbench is a short active/retired/submitted landing; a proposal room holds actual drafting, requirements and current assembled output. Its guide is optional reading, not the entrance fee to writing.

## Evidence: Findings and Results Stay Visible

Lead with the question and supported finding; show date/conditions, actual results/charts, short interpretation, defensible conclusion and limitations. Collapse long methodology, sources and reconciliation details. Keep deliverables/downloads reachable.

A compact home links to the report; it does not hide the report's results inside another toggle. Retain source roles, exact consequential conditions and uncertainty. Studying a report's layout does not independently validate its measurements or chart pixels.

When new charts are requested, the separate personalized-charts skill can supply chart conventions if available; do not impose hardware strips/branding on unrelated pages or invent numeric evidence.

## Handoff: Resume Without Reconstruction

Start with the latest checkpoint and stopping point. State what actually changed, important limits, source route, exact next action and blockers. Preserve prior dated checkpoints as history when superseded, without rewriting their original meaning.

Credit actual contributors. A source saying another AI completed a read remains that AI's reported evidence unless independently inspected. Distinguish a contribution, a review and an execution result.

## Deep Guide and History

A deep guide can use purpose/audience, a short overview, progressively deeper explanations, responsibility map, question-based reading routes and source/current-maturity map.

For a long Human Guide, research page or Plan whose table of contents crowds the opening, place the native TOC inside a clearly labeled native toggle near the start that begins collapsed. Keep the short orientation, example/next action and direct working/resume/AI routes visible. This is purpose-appropriate disclosure, not a rule to hide short navigation or the selected software recipe's operative board. Preserve the full headings/body and exact heading destinations; verify opening/closing the toggle and representative heading links in the real rendered page when visual access is available.

History records dated context, observation/result, lessons, current implications and links. Keep history because it explains change; do not let older "now" wording override current evidence/authorization. These can share one room until separation helps.

## Lightweight Reading or Registry Card

Properties alone can carry identity/source, why it matters, status, subjective load, resume position and next step. A blank body is legitimate when knowledge already lives in its real source. Do not add empty headings or duplicate a full guide to make records look uniform.

## Education: Learn, Practice and Return

For a course or teaching hub, lead with who it helps, the learning outcome, where to begin and how to resume. Shape the main route around chapters/lessons and useful practice, with explanations and visual aids where they teach. Keep essential instructions and the next lesson visible; use native collapsibles for deeper explanations and source material without hiding prerequisites.

Adapt pacing, examples and any progress tracking to the learner and supplied evidence. Unknown mastery stays unknown. A course does not need software phases, releases, milestone Boards or an inline work database merely because the optional software recipe exists. Add a tracker only when it serves the learning workflow; keep an intentional property-only reading record valid.

Reference: [AI Education Home](https://app.notion.com/p/3d4bd7ade63b81b39fd6c7f24f6b8d7f), its [reader's guide](https://app.notion.com/p/3f9bd7ade63b8175bdacc1099a194403) and [Chapter 01](https://app.notion.com/p/3d4bd7ade63b81fa92accf201decfcc8) show welcoming audience/context, multiple purposeful reading routes, concept-first parts, question-led explanation, worked examples, conceptual illustrations and collapsed deeper sources. Use the organization, not its curriculum length, technical facts, media or dated product claims. This bounded navigation/layout read does not re-verify teaching facts or authorize changing the source hub.

## Visual Grammar

- Native blocks and meaningful icons; avoid repeating the same emoji in both page icon and title. Use emoji plus readable text as stable semantic identifiers across schema options, properties, views and their explanations. Reuse established symbols for the same meaning; do not silently rename labels or scatter decorative emoji. Symbols and color never replace accessible words.
- Restrained callouts: blue can orient, green confirm, amber mark pending decisions and gray hold background. These are adaptable conventions, not a universal status code.
- Text carries meaning without color. Options are internally consistent within their field; red Safety/Area is not automatically failure.
- Clear hierarchy, readable spacing and compact labels. A cover is optional; control centers can work without one.
- Columns only for useful short comparisons/navigation. Avoid wide five-column density without a real benefit and check narrower viewing sizes where tools permit.
- Use actual native toggles for background, not text pretending to collapse. Use real records and saved Board/Gallery views, not decorated prose pretending to be cards.
