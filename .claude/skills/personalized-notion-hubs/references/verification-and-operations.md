# Live Operations and Verification

## Capability and Authorization

This skill is a local method, not a connection or permission grant. Discover the actual Notion tool names and current schemas in the session. Use an available connector or authorized browser route; do not invent MCP endpoints, credentials, subscriptions or tool authority. Do not bypass an access restriction.

Before mutation establish target, scope, operation and preservation requirements. A request to install this skill alone does not authorize hub edits, shared-access changes, Registry writes, imports or project execution. Future explicitly authorized hub work can be performed within its own boundaries without asking approval for every harmless formatting choice.

If private access fails, report the actual error/entity and ask for an export/pasted brief. If native database/view or permission operations are unsupported, deliver a labeled build specification and identify what is still unsaved/unverified. Browser use must follow its applicable skill/session instructions.

## Inspect and Preserve

1. Locate the intended hub, Registry entry and existing canonical sources; avoid duplicates.
2. Read target and relevant child pages/record bodies. Inspect database/data-source schema and saved views, not titles alone.
3. Record entity IDs, parent path, links, useful record counts, source roles/dates and uncertainty. Check truncation, unknown blocks and pagination; omission of completeness metadata is not proof of exhaustive coverage.
4. Distinguish current user authorization from historical plans. Compare consequential status claims with their actual evidence; do not silently rewrite discrepancies.
5. Preserve native children, record IDs, rich text/mentions, relations, formulas, attachments, meaningful history and user edits. Prefer targeted changes to replacing a whole parent.

In connectors that return enhanced Markdown, a child-page/database block can reparent or move an object when written. A native mention is a link. Inspect the current Markdown specification before structural round-trips; do not substitute a child block just to make navigation.

## Starter Duplication: Unproven Remapping

The October 11 starter's duplication/remapping has not been tested. A successful duplicate call does not prove internal links were remapped.

Before editing a copy:

- Capture master hub/children/database/data-source/view IDs.
- Fetch the copied hierarchy. Confirm owned children and a genuinely independent data-source identity before touching copy records.
- Map old to copied page/database/view IDs. Compare copied mentions, direct saved-view URLs, record sources, relations and any template defaults/formulas that reference old objects.
- Remap only links meant to be internal. Preserve intentionally external governing/evidence sources; not every old link should change.
- Inspect relation targets and representative copied records; verify no edits will change master/live-project rows.
- Replace/remove demos in the authorized copy only, or retain clearly labeled templates if requested. Leave the master unchanged.
- Read back navigation and query actual view memberships. Do not claim automatic remapping or a changed global default tab.

If the copy still depends on the live/master source, stop dependent record writes. Explain what needs native repair or a human action instead of asserting the copy is safe.

### Mandatory software inside-Home gate and blocked-visual handoff

For an explicit inside-Home software request, visual verification is a required acceptance gate even when access is unavailable. It is not waived by a successful connector write/readback. Verify actual rendered board columns/cards on Home, intended tabs switching that same in-Home surface, representative card open/return, shared canonical identity and record preservation. Run the [software recipe's desktop/narrow regressions](software-development-project-hub.md), including wrapping, scrolling, overflow and column access at recorded widths.

Record configuration, rendering and owner acceptance separately. An owner report that the board is outside Home means **presentation failed**; retain that result until an actual rendered repair/recheck passes. A presentation never visually tested is **unverified**. Neither status means data loss, and neither can be promoted to fixed from `inline=true`, source/child links, view IDs, counts or schema checks. Education acceptance is scoped to education and cannot validate a database presentation.

If visual access is blocked, stop short of claiming presentation completion and leave this bounded handoff:

- Exact Home, canonical data-source and linked-presentation/view IDs/URLs; existing record population and preservation evidence.
- The requested in-Home behavior, owner-reported failure and date, plus separately supported configuration checks.
- The actual tool/access error and checks not performed; do not infer a general capability from a skill name or another thread's result.
- A coordinated authenticated-browser or owner-screenshot route showing Home, the intended tabs, card open/return, desktop and narrow behavior. Screenshots can establish visible placement, but tab/card interactions and source identity still need their corresponding evidence.
- The next authorized inspection/repair/recheck and exact unresolved gate. Preserve existing records, sources and history; do not change sharing, bypass access restrictions or create duplicate sources/cards as a blind repair.

This handoff does not itself authorize physical hub changes, screenshots containing unrelated private material or additional desktop control.

**Delivery**

Return saved hub and main-view links; concise adaptation/changes and preservation; factual evidence basis; unresolved native, visual, access, duplication or freshness limits; concrete next step if blocked. For local drafts explicitly say no live Notion change was made. For skill installation distinguish disk packaging/validation, automatic-invocation policy and actual runtime discovery.

## Avoid False Equivalence

| Evidence | What it does not prove |
| --- | --- |
| Page heading or decorated text | Native database, Board or Gallery exists |
| Tool listed in the session | Private read/write/view capability works |
| View-specific URL | Global default tab or tab order changed |
| Saved view configuration | Browser appearance or all-record completeness without query/pagination |
| `inline=true`, a child/source link, record count or API success | Actual native board visible on Home, working in-Home tabs or card open/return |
| Educational owner acceptance | Software/database rendering acceptance |
| Blank reading body | Incomplete record when properties already do the job |
| Recent page edit | Every embedded status is fresh |
| Copied starter page | Independent database or remapped links/relations |
| Source-reported acceptance | Independent reproduction of its tests |
| Skill files on disk | Current chat has loaded/discovered the new skill |
